# 09. Plan

## Method

Spec first: documents, then code that traces to them. The chief agent (Fable) owns intent, architecture, decomposition, tradeoffs, and final review. Execution goes to cheaper agents by risk tier:

* **Opus** — high-risk work: auth, migrations, RLS, secrets, webhook signing, queues, the public API. Opus implements it or reviews it before merge.
* **Sonnet** — scoped implementation, tests, UI wiring, adapters that follow a written spec.
* **Haiku** — discovery, file summaries, checklist verification, trace checks.

Every phase ends with four things: green checks (`biome check`, `tsc --noEmit`, `bun test`, and the integration tests where they apply), a short report in `docs/reports/`, a commit, and a push to `origin/feat/v1-platform` (ADR-011). A pull request into `master` opens when the definition of done holds (P8).

Each report states three items: what was done, what was verified, and what risk remains. Reports are named `P<n>-<slug>.md`.

Requirement ids are in 02.requirements.md. ADR ids are in `docs/decisions/`.

## Risks

| Risk | Effect | Mitigation |
|---|---|---|
| `backend-uatis` does not deliver customer webhooks yet (ADR-002) | No real inbound messages by webhook | The reconciliation poll (FR-107) and `FakeGateway`. Record the gap in the P5 report. |
| `web-nf` needs a CSC and certificate for NFC-e in homologação | Invoice smoke test may stay blocked | Contract tests with `FakeInvoiceGateway`; smoke test is best effort (T6.10). |
| pg_cron seconds-level schedules need `pg_cron` 1.5 or later | The 30-second poll may not run | ADR-015: Supabase ships 1.6. Check the local image version in T2.8; fall back to one-minute cron plus a worker loop. |
| `backend-uatis` has no idempotency key on `POST /v1/messages` (ADR-017) | A retry after a timeout could send a message twice | The worker does not retry after a timeout or a 5xx. The message is `failed` with `ambiguous`. Follow-up in `backend-uatis`. |
| Restaurant NCM, CFOP, and CST defaults in 08 are unverified | Wrong tax codes on a real invoice | Settings shows "Confirme com o seu contador". An accountant must confirm before production. |
| Many parallel agents touch shared packages | Merge conflicts | Each task owns one package or screen; ports (T3.7) are fixed first. |
| Realtime and RLS interplay | Missing or leaked events | Test with two sessions in T2.12 and T4.4. |
| The AI places a wrong order (P10) | A customer gets food they did not ask for | Server-rendered summary and the FR-186 guard; orders start as `aguardando` unless auto-accept is on; the eval suite blocks the phase below 90%. |
| AI cost grows with traffic (P10) | An unexpected Anthropic bill | `claude-haiku-5-5`, the plan quota, pay-by-usage overage, `monthly_hard_cap`, prompt caching, and token counts in `ai_runs`. |
| Haiku 5.5 misreads orders (P10) | Wrong carts or many handoffs | The confirmation summary; the eval gate; `MT_AI_MODEL` switches to `claude-sonnet-5-5` without a code change. |

## Notes: inconsistencies found, and the ADR that settled each

These came up while the documents were written. Each has a decision in an ADR or in a requirement.

1. The goal lists `apps/generation-api` and doc 08 as the municipality template system. ADR-001 drops `generation-api`. The brief and ADR-013 redefine 08 as `08.fiscal-mapping.md`. The goal text is stale on both points. The goal also names NFSe sandboxes (Publica/Irani) in its definition of done. Marmitop does not issue NFSe (ADR-003). Doc 03 keeps the NFSe background; no NFSe sandbox test exists.
2. The goal says the settings screen has "outbound webhook URL and API key". ADR-009 makes the API key an integrator credential, not a webhook credential. The requirements follow ADR-009 (FR-087, FR-089).
3. The brief data model has a `webhook_endpoints` table (several rows), but ADR-009 allows one URL per restaurant in v1. FR-087 allows one enabled endpoint; the table shape is ready for more.
4. The goal says "connect a WhatsApp number". ADR-002 connects the restaurant to a `backend-uatis` instance (URL, key, secret, `phone_number_id`). FR-085 follows ADR-002.
5. The goal says "inbound webhook with signature verification" for the WhatsApp Business Cloud API. Marmitop verifies the `backend-uatis` signature (`X-Uatis-Signature`). `backend-uatis` verifies the Meta signature. FR-102 follows ADR-002.
6. ADR-003 says an invoice can be issued for an order that is `entregue` or `pronto`/`saiu`. A pickup order never reaches `saiu`. FR-121 states the rule as "has reached `pronto`, `saiu`, or `entregue`, and is not `cancelado`".
7. Prototype settings have "Regras de resposta" toggles and a generic integration list. Neither is in the goal. FR-097 removes them.
8. The prototype counts "Clientes ativos" as all contacts. The goal says "active customers" without a definition. FR-073 defines it as customers with a counted order in the period.
9. The goal does not say which orders count as revenue. FR-070 counts `entregue` only, which matches the board KPI "Faturamento entregue".
10. The `closed` automatic message could repeat on every inbound message. The goal does not say. FR-111 sets at most one per conversation in 12 hours. Decided in ADR-015.
11. Who may issue or cancel an invoice is not in the goal. ADR-015 decides: attendant and admin issue, only admin cancels (FR-135).
12. Plan limits are shown but not enforced in v1 (FR-155). The goal says only "usage metering, plan display, invoice history placeholder". Decided in ADR-015.
13. ADR-002 sets the poll to every 30 seconds with pg_cron. Older `pg_cron` versions accept minutes only. ADR-015 confirms Supabase ships pg_cron 1.6, which accepts `30 seconds`.
14. The goal asks for the "technical-writer" skill. ADR-010 replaces it with `orwell-writing`. No conflict.
15. Doc numbering: the goal lists doc 08 as `08.validation-templates.md`. The file is `08.fiscal-mapping.md` per ADR-013.
16. The brief let an order move one step forward at a time. ADR-017 allows forward skips, one step back, no `saiu` for pickup, and final `entregue` and `cancelado`. FR-022 follows ADR-017.
17. The goal does not cover the WhatsApp 24-hour service window. ADR-014 adds template sending for `order_received` outside the window and a `422 outside_service_window` for manual replies (FR-117).
18. The brief stored a free-text address. ADR-016 replaces it with structured fields and an invoice pre-check (FR-034, FR-125). v1 has no CEP lookup.
19. The brief said API orders use `phone` as the source and that test keys use fake gateways. ADR-017 sets `source = api` and makes `mtk_test_` and `mtk_live_` behave the same.
