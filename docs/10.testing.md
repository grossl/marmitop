# 10. Testing

## Strategy

Four layers, all run by `bun test` (and Playwright for the last) through Turborepo. Untested code does not merge (NFR-050, NFR-053). Tests name the requirements they cover: `// covers FR-021, NFR-001`.

| Layer | Scope | Dependencies |
|---|---|---|
| Unit | pure logic in `packages/core`: order totals, status machine, business hours, automatic-message rules, report aggregation, signing and verification | none; no I/O, injected `Clock` |
| Integration | SQL migrations, RLS, role permissions, pgmq flow, services in `packages/http` | a real Postgres with pgmq: database `mt_test` on the local Supabase stack, or `TEST_DATABASE_URL` |
| API | Hono routes in `apps/api`: public API, inbound webhooks | `app.request` against the real app; real Postgres; fake gateways |
| End-to-end | the dashboard flow of the Definition of done | Playwright; local Supabase stack; `FakeGateway` and `FakeInvoiceGateway` |

Fakes are production-quality code in `packages/core`. `FakeGateway` implements `WhatsAppGateway` (ADR-002). `FakeInvoiceGateway` implements `InvoiceGateway` (ADR-003). Both record calls and let a test script the next response, failure, or delay.

## Unit tests (`packages/core`)

Files sit next to sources: `order-total.test.ts`, `order-status.test.ts`, and so on. A `Clock` port replaces `Date.now()`, so every time-based rule is deterministic.

* **Order totals** (FR-030–039, ADR-006) — `total = sum(unit_price × qty) + delivery_fee`; fee applies to delivery only; pickup has zero fee; sizes use the size price, not the base price; integer cents, no float drift; unavailable item or weekday not offered is rejected; empty cart is rejected; a later price change leaves a stored snapshot unchanged.
* **Status transitions and history** (FR-021–029, ADR-017) — forward moves may skip columns (`aguardando → preparando` writes one history row); pickup never enters `saiu`; backward moves go one step only; any non-final status to `cancelado`; no move out of `entregue` or `cancelado`; the same status again is a no-op with no history row; each accepted change yields one history record (`from_status`, `to_status`, `changed_by`, `changed_at`); a rejected change yields none. A table test runs every `(from, to, fulfillment)` triple through `canTransition` and through the database trigger and asserts they agree.
* **Business hours** (FR-083, FR-113) — open and closed inside a day; boundary minutes (opens inclusive, closes exclusive); overnight windows (for example 18:00–02:00, checked on both sides of midnight and against the previous day's row); disabled weekdays; timezone `America/Sao_Paulo` against a UTC instant; a different timezone setting; days with no row count as closed.
* **Service window** (FR-117, ADR-014) — inside the 24-hour window free text is sent; outside it with a configured template the template is sent; outside it without a template nothing is sent and the message is `failed` with `outside_service_window`; a manual reply outside the window returns `422 outside_service_window` and stores nothing.
* **Automatic-message triggers** (FR-110–115) — `welcome` fires on the first inbound message of a new conversation; `closed` fires when the restaurant is closed and at most once per conversation in 12 hours (ADR-015); `order_received` fires on order creation from chat; a disabled kind never fires; the body renders its placeholders; no message goes out for an outbound-only conversation.
* **Report aggregations** (FR-070–079) — revenue counts `entregue` orders only; order count, average ticket (integer division rule fixed and tested), active customers; revenue for the last 6 calendar months with empty months at zero; orders per day for the last 14 days with empty days at zero; top-selling items by quantity with a stable tie-break; day boundaries use the restaurant timezone.
* **Webhook signature** — see below.

### Webhook signature tests

Three systems use one scheme: header `t=<unix>,v1=<hex HMAC-SHA256(secret, "t.body")>` (ADR-002, ADR-003, ADR-009). One shared verifier in `packages/core` serves all three, and the same cases run for each header name.

| System | Header | Direction | Used for |
|---|---|---|---|
| backend-uatis | `X-Uatis-Signature` | inbound | verify WhatsApp events (FR-102) |
| web-nf | `X-NF-Signature` | inbound | verify invoice events (FR-126) |
| Marmitop | `X-Marmitop-Signature` | outbound | sign deliveries to the restaurant's URL (FR-147) |

Cases, for each: valid signature passes; tampered body fails; wrong secret fails; timestamp older or newer than 5 minutes fails; missing header, missing `t=`, missing `v1=`, and non-hex `v1` fail; comparison is constant time (the test asserts the use of the shared compare function, not timing); multiple `v1` values (rotation) pass if any matches; `sign` output verifies with `verify`; `sign` matches a fixed known vector computed by an independent implementation (Node `crypto`).

## Integration tests (real Postgres)

Integration tests run against a separate database, `mt_test`, on the local Supabase stack's Postgres cluster (port 54422). The machine has Docker and the Supabase CLI but no local Postgres binaries, and the Supabase image already ships the Supabase roles and the pgmq extension. The dev database (`postgres`) is never touched, so tests may truncate freely.

1. Reach the cluster as the migration owner (`MT_TEST_ADMIN_URL`, default the stack's `postgres` login), or use `TEST_DATABASE_URL` as-is when set (CI service container with pgmq available).
2. Create `mt_test` if it is missing. If an applied migration file changed (checksum differs from the ledger), drop and recreate it.
3. `create extension pgmq`, and create stand-ins for the Supabase surface the migrations touch in a non-Supabase database: `auth.users` and `auth.uid()` reading `request.jwt.claim.sub` or `request.jwt.claims`. Policies call only `auth.uid()`, so RLS behaves the same.
4. Run every pending file from `supabase/migrations/` (ledger `public._mt_test_migrations` with a sha256 checksum, see 11.operations.md), then let the connecting role `set role` to `app_service`, `authenticated`, and `anon`.
5. Each test file resets state with truncation or a rolled-back transaction.

`packages/db/src/test-database.ts` does steps 1–4 under an advisory lock. The harness (`packages/db/src/test-harness.ts`) calls it on first use, and `bun scripts/test-db.ts` (`bun run db:test`) runs it by hand. pg_cron lives only in the cluster's `postgres` database, so 0012 skips the schedules in `mt_test`; Realtime and Storage are absent there too, so 0013 and 0014 skip. The scheduled functions (reconciliation enqueue, retention trims) are plain SQL and are tested by direct call. The schedule is configuration, checked by `scripts/dev-seed/verify.ts` on the dev database and by the runbooks.

The integration tests are part of `bun run test`. They need the local stack: run `bun run dev:stack` (or `supabase start`) first. Without a reachable database they fail with a message that says so; they never skip silently.

What the integration layer proves:

* **RLS cross-tenant isolation** (NFR-001) — for every table with `restaurant_id`: seed restaurants A and B; read as a member of A on the user path and on the `app_service` path (`app.restaurant_id` set); assert zero B rows; assert writes across the boundary fail; a missing `app.restaurant_id` yields zero rows. A meta-test lists all tables from `information_schema` and fails if a tenant table lacks RLS or lacks a test entry, so a new table cannot ship unprotected.
* **Role permissions** (FR-001–009, ADR-005) — `attendant` can read and write messages, orders, contacts; cannot write menu, stock, settings, API keys, or integrations; `admin` can do all. Services in `packages/http` enforce this; the test calls the services as each role and asserts `forbidden`. RLS is the backstop and gets its own cases. A user with no membership sees nothing.
* **Order flow** — `createOrder` allocates `ORD-NNN` per restaurant without gaps under concurrent calls; writes `order_items` snapshots; `changeOrderStatus` writes history in the same transaction; an illegal transition rolls back.
* **Queue jobs** (ADR-007) — enqueue on the same transaction as the trigger (automatic messages, outbound messages, webhook deliveries, invoice jobs); worker consumption; visibility timeout; archive on success; backoff at 1m, 5m, 30m, 2h, 8h with a `job_attempts` row per try; permanent failure stops retrying; duplicate delivery does not send twice (idempotency by `external_id` and by `Idempotency-Key`).
* **Inbound upsert** — the same `external_id` delivered twice, by webhook and by poll, yields one `messages` row; `last_sync_cursor` advances only after a successful batch; status updates move forward only (`sent → delivered → read`, never backward).
* **Secrets** (ADR-012) — round trip under a test `MT_KEK`; wrong KEK fails; a role without access cannot read `secrets` rows of another restaurant; no log line or API response holds plaintext.
* **Stock and API keys** (FR-060–069, FR-141) — movements update `current_qty`; low-stock query; a revoked key fails lookup; only the hash is stored; lookup runs on the unique hash (ADR-017).
* **Send retries** (FR-108, ADR-017) — a connection error before the request left retries with backoff; a timeout or a 5xx after the request left gives one attempt, `failed`, and `error_code = ambiguous`; no automatic resend.
* **Address and invoice pre-check** (FR-034, FR-125, ADR-016) — a delivery order needs `logradouro` and `bairro`; "Emitir NF" for a delivery order without CPF/CNPJ or `codigo_municipio` creates no invoice row; a retry resends the stored `request_payload` unchanged.
* **Browser write lockdown** (NFR-001, ADR-017) — the `authenticated` role cannot insert, update, or delete on any table through PostgREST, except admin uploads to `menu-images`.

## API tests (`apps/api`)

Hono tests call `app.request(...)` with no open port, against the real Postgres harness and fake gateways. Files: `*.test.ts` for pure route logic, `*.integration.test.ts` for routes that touch the database.

* **Inbound WhatsApp webhook** (`POST /v1/webhooks/uatis/{restaurant_id}`) — valid signature stores the message, creates the conversation and customer, triggers the `welcome` message; bad signature gives `401`; stale timestamp gives `401`; unknown restaurant gives the same `401` as a bad signature (FR-118); duplicate event is accepted and stored once; a restaurant cannot be reached with another restaurant's secret.
* **Inbound invoice webhook** (`POST /v1/webhooks/web-nf/{restaurant_id}`) — signature checks as above; `invoice.authorized`, `rejected`, `denied`, `cancelled` update `order_invoices` and fire `invoice.updated` outbound.
* **Public API** (FR-140–145; `mtk_test_` and `mtk_live_` keys) — missing, malformed, unknown, and revoked keys give `401`; a key sees only its restaurant; list and create orders (an API order has `source = api`); both key kinds reach the same data and the same gateways, which only `MT_UATIS_FAKE` and `MT_WEBNF_FAKE` choose; `POST /v1/messages` outside the 24-hour window gives `422 outside_service_window`; invalid payloads give a `422` with field paths; `last_used_at` updates.
* **Outbound webhooks** — a status change creates a `webhook_deliveries` row; the worker pass signs the body, posts to a local stub server, and records `last_status_code`; `5xx` retries on schedule; `2xx` stops; redirects are not followed; private hosts are refused when the SSRF guard is on.
* **Health** — `/v1/health` answers without a database check failing open.

## Dashboard end-to-end (Playwright)

Files are `*.e2e.ts` under `apps/dashboard/e2e/`. They need a real Supabase Auth, so they run against the local CLI stack (`bun run dev:stack`, see 11.operations.md) and are gated by `WEB_E2E=1`. They are not part of the hermetic CI suite. Both gateways are the fakes: the app starts with `WHATSAPP_GATEWAY=fake` and `INVOICE_GATEWAY=fake`, and the dev-only "Simulate customer message" control injects inbound messages (ADR-002).

Run with `WEB_E2E=1 bun run --cwd apps/dashboard e2e`.

| File | Flow |
|---|---|
| `dod-flow.e2e.ts` | the Definition of done flow, in one scenario (item 2 below) |
| `new-order.e2e.ts` | counter order appears on the board in real time (item 3) |
| `roles.e2e.ts` | attendant sees only messages, orders, new order, contacts; admin sees all |
| `no-mock-data.e2e.ts` | each screen reads database rows: after a reset it shows its empty state, and after the flow creates a row it shows that row (ADR-024); a grep test asserts nothing imports `lib/marmita-data.ts` (item 4) |

`dod-flow.e2e.ts` steps: log in as admin → set profile, hours, and automatic messages → connect a WhatsApp number (fake gateway) → register a meal with sizes → simulate a customer message → see the unread count and the automatic reply → reply from the dashboard → create the order from the chat → drag the card through the board to `entregue` → open Reports and see the order in revenue and count → issue an NFC-e with `FakeInvoiceGateway` and open the XML link.

## Testing against the real neighbours

Default test runs never reach a real web-nf or backend-uatis. Two manual suites check the adapters against the real services. They run only when their flag is set, like `WEB_E2E`.

### web-nf (homologação)

Gate: `NF_E2E=1`. Files: `apps/worker/e2e-nf/issue-nfce.ts` (the runner) and `apps/worker/e2e-nf/scenario.ts` (the steps).

1. Start the local web-nf stack (in `/Users/grossl/projects/web-nf`: `bun run dev:stack`, then `bun run dev`). The generation API listens on `3002`; Marmitop never shares it. Its database must be up: the key lookup needs it, and without it every authenticated call hangs until Marmitop's 10-second timeout.
2. In the web-nf dashboard, create an organization in `homologacao`, upload a test certificate, register the NFC-e CSC for `homologacao`, and create a key with the `nfk_test_` prefix. The runner refuses any key without that prefix.
3. Export `NF_E2E=1`, `NF_E2E_BASE_URL` (for example `http://localhost:3002`), `NF_E2E_API_KEY` (the `nfk_test_` value), and `MT_ALLOW_PRIVATE_HOSTS=1` for a localhost URL. `NF_E2E_TIMEOUT_MS` (default 120000) bounds the wait for a final state.
4. Run `bun apps/worker/e2e-nf/issue-nfce.ts`. Through the real `WebNfGateway` it calls `testConnection`, issues an NFC-e built by core `buildInvoiceRequest` from a pickup fixture order, replays the same key and body (expects `Idempotency-Replayed`), polls `GET /v1/invoices/{id}` to a final state, and then: on `authorized`, checks the number, the key, and the XML URL, posts a `cancelamento` event, and reads the event back; on `rejected` or `failed`, checks that the error maps to a pt-BR hint (08 section 8.3). It prints ids and states, never the key or a signed URL. Exit code 0 means every step passed.
5. To see the webhook path, start `apps/api`, point the web-nf webhook at `http://localhost:3101/v1/webhooks/web-nf/<restaurant_id>` with the secret saved in Settings → Fiscal, run "Emitir NF" from the dashboard with the worker running, and check `order_invoices` moves to `authorized` before the first poll.
6. Record results in `docs/reports/`.
7. Dry run without web-nf: `apps/worker/src/e2e-nf.dry-run.test.ts` runs the same scenario in `bun test` against `FakeWebNfServer` (`packages/http/src/testing/fake-web-nf-server.ts`), which returns the shapes web-nf really returns.

Against a local web-nf, SEFAZ transmission may fail with a development certificate. The suite then checks the mapping and the error path (`rejected` with `error_code` mapped as in 08.fiscal-mapping.md), not authorization.

### backend-uatis (obk_test_)

Gate: `UATIS_E2E=1`. Files: `apps/worker/e2e-uatis/*.ts`.

1. Start backend-uatis locally (see its README; its api listens on 3301).
2. Create a key with the `obk_test_` prefix. The runner refuses an `obk_live_` key.
3. Export `UATIS_E2E=1`, `UATIS_E2E_BASE_URL` (for example `http://localhost:3301`), `UATIS_E2E_API_KEY`, `UATIS_E2E_PHONE_NUMBER_ID` (the line), `UATIS_E2E_TO` (a test customer number), and `MT_ALLOW_PRIVATE_HOSTS=1` for a localhost URL.
4. Run `bun apps/worker/e2e-uatis/send-and-poll.ts`. It calls `testConnection` and `listApprovedTemplates`, sends a text through `UatisGateway` (expects `201` with `pending`, or `422 outside_service_window` when the number has not written in 24 hours), then polls `GET /v1/messages` from five minutes ago in both directions and checks the mapping. Exit code 0 means every step passed.
5. Webhooks and the event feed (ADR-021, ADR-023). With backend-uatis running its feed and an `admin` test key, press "Ativar webhook" in Settings: locally it registers pull, and a WhatsApp message appears in Mensagens within a few seconds. Without backend-uatis, start `apps/api` and run `bun apps/worker/e2e-uatis/replay-webhook.ts` with `UATIS_E2E=1`, `MT_API_URL`, `UATIS_E2E_RESTAURANT_ID`, `UATIS_E2E_WEBHOOK_SECRET` (the stored `uatis_webhook_secret`), optional `UATIS_E2E_ORGANIZATION_ID` (when `uatis_organization_id` is set), and optional `UATIS_E2E_FROM` (digits, as backend-uatis stores them). It posts the exact backend-uatis push body and headers and expects `200`, `200` (same event re-signed, deduplicated by event id), `401` (wrong secret), and `401` for another organization when the organization is set. Unit and integration coverage: `apps/api/src/routes/webhooks/uatis-real-format.test.ts`, `packages/http/src/services/admin/uatis-webhook.integration.test.ts`, `apps/worker/src/handlers/uatis-feed.test.ts`, the feed tests in `apps/worker/src/worker.integration.test.ts`, and the cadence tests in `packages/db/src/queue.integration.test.ts`.
6. Dry run without backend-uatis: the same steps run in `bun test` against `FakeUatisServer` (`packages/http/src/testing/fake-uatis-server.ts`), which returns the shapes backend-uatis really returns.

## AI order assistant suites (P10)

Source: 12.ai-order-assistant.md "Testing", ADR-025, FR-180–199.

* **Unit (core, no I/O).** Cart validation and `missing`; the `place_order` guard; the quota state; history-to-messages mapping (role merge, prefixes, 20-message window); the debounce decision; the summary renderer (BRL text, pickup, delivery with and without `complemento`).
* **Integration (database, `ScriptedAssistantModel`).** Full delivery order from first message to an `orders` row with `source = 'whatsapp'`, `payment_method = null`, and `ai_run_id`; pickup order; a burst of 3 messages gives one run; an attendant reply during the delay gives `paused`; `place_order` without confirmation fails; a cart changed after the summary fails; quota blocks with overage off and allows with overage on; the hard cap blocks; one `ai.reply` usage row per trigger message, also after a retry; a customer message sent during a running turn gets its own turn; a shutdown abort retries with no pause and a budget abort pauses with `model`; tenant isolation for every tool; stale job.
* **Contract.** `AnthropicAssistantModel` maps recorded responses with `tool_use`, `end_turn`, and `refusal` to the port types.
* **Evals (real model, manual).** `bun run --cwd apps/worker eval:ai` runs about 25 pt-BR conversations against the real model with a scripted customer. It grades the final cart or order, not the wording. It prints the pass rate and the cost. It is manual and costs money. It is outside `bun run test` and outside CI. It needs `ANTHROPIC_API_KEY`.

## Order status message suites

Source: ADR-026, FR-200–205.

* **Unit (core, no I/O).** `orderStatusMessageKind` maps each target status to its kind. A forward skip gives only the target's kind. A back step and a no-op give none. `order_ready` is for pickup only. `decideOrderStatusMessage` covers the three window cases (free text, template, `failed` with `outside_service_window`), a disabled kind, no conversation, and a kind already sent.
* **Integration (database).** A dashboard move writes one `pending` row with `sent_by` null and one outbound job. The status at creation sends nothing. A forward skip sends only the target's kind. A back step and a no-op send nothing. `pronto → preparando → pronto` on a pickup order sends `order_ready` once. A delivery order at `pronto` sends nothing, and `saiu` sends. A counter order sends nothing. Cancel sends. A disabled kind sends nothing. Outside the window with no template, the row is `failed` and has no job. The public API (`apiChangeOrderStatus`) and the system actor send. A rolled-back status change leaves no row and no job.
* **Migration.** On a throwaway database, 0021 inserts the six rows with the ADR-026 texts and on/off values for every restaurant that exists before it runs, and keeps the other rows.

## CI

One pipeline on every push and pull request (ADR-011 has one branch, `feat/v1-platform`, until the pull request into `master`):

1. `bun install --frozen-lockfile`.
2. `bun run lint` (Biome) and `bun run typecheck`.
3. Start a Postgres service container with the pgmq extension available (the `supabase/postgres` image) and set `TEST_DATABASE_URL`; the harness creates the extension, the auth stand-ins, and runs the migrations.
4. `bun run test` through turbo: unit, integration, and API tests.
5. `bun run build` for the dashboard, API, and worker.

The pipeline blocks the merge on any failure. Playwright (`WEB_E2E=1`) and the neighbour suites (`NF_E2E=1`, `UATIS_E2E=1`) are not in the required pipeline. A separate manual or nightly job can run `WEB_E2E` against the local stack. No real key, certificate, or Meta credential ever enters CI.

## Conventions

* Test files sit next to sources: `foo.test.ts`.
* Integration tests live in `*.integration.test.ts` and use the harness from `@mt/db/test-harness` (`packages/db/src/test-harness.ts`).
* End-to-end files are `*.e2e.ts` and run only with `WEB_E2E=1`.
* Each test cites its requirement: `// covers FR-xxx`.
* Tests never read the wall clock or the network. They inject `Clock` and the fake gateways.
* Fakes are typed, documented, and checked by the same contract tests as the real adapters.
