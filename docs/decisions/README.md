# Architecture decision records

ADR-014 to ADR-017 amend earlier ADRs. When two ADRs conflict, the newest wins. ADR-002 has an Amendment 1 for facts found while writing the API spec, and ADR-021 amends ADR-002 again (Amendment 3).

| ADR | Title | Decision |
|---|---|---|
| [001](ADR-001-monorepo-layout.md) | Monorepo layout | Bun workspaces and Turborepo with `apps/dashboard`, `apps/api`, `apps/worker`, and shared `packages/`. No `generation-api`. |
| [002](ADR-002-whatsapp-via-backend-uatis.md) | WhatsApp channel through backend-uatis | Send and receive through `backend-uatis`, with its webhooks and a 30-second reconciliation poll. The poll was required while its webhooks were not delivered (Amendment 1); ADR-021 makes the webhook the main path. |
| [003](ADR-003-invoices-via-web-nf.md) | Invoices through web-nf | Issue NFC-e and NF-e through `web-nf`. No NFSe in v1. |
| [004](ADR-004-dashboard-data-access.md) | Dashboard data access | The dashboard reads and writes through server-side services on `app_service`. The browser uses Supabase for Auth and Realtime only. |
| [005](ADR-005-auth-tenancy-roles.md) | Auth, tenancy, and roles | Supabase Auth, one restaurant per tenant with RLS, and two roles: `admin` and `attendant`. |
| [006](ADR-006-money-and-order-totals.md) | Money and order totals | Money is integer cents. The server computes totals and snapshots item names and prices. |
| [007](ADR-007-queues-and-jobs.md) | Queues and jobs | pgmq queues and pg_cron schedules, with idempotent jobs, backoff, and a `job_attempts` log. |
| [008](ADR-008-billing-interface.md) | Billing interface | A `BillingProvider` port with a null adapter. Usage is recorded and no provider is wired. |
| [009](ADR-009-outbound-webhooks-and-api-keys.md) | Outbound webhooks and API keys | Signed outbound webhooks to one URL per restaurant, and hashed `mtk_` API keys for integrators. |
| [010](ADR-010-document-style-skill.md) | Document style skill | Documents follow the `orwell-writing` skill. |
| [011](ADR-011-branch-and-push.md) | Branch and push | Work on `feat/v1-platform`, commit and push per phase, and open one pull request into `master`. |
| [012](ADR-012-secret-storage.md) | Secret storage | Per-restaurant secrets are encrypted in the `secrets` table with envelope encryption under `MT_KEK`. |
| [013](ADR-013-doc-08-fiscal-mapping.md) | Doc 08 becomes the fiscal mapping | `08.validation-templates.md` is replaced by `08.fiscal-mapping.md`: how an order becomes a `web-nf` request. |
| [014](ADR-014-whatsapp-service-window.md) | WhatsApp 24-hour service window | Send free text inside the window and an approved template for `order_received` outside it. With no template, mark the message `failed`. |
| [015](ADR-015-v1-product-rules.md) | v1 product rules | `closed` message once per conversation in 12 hours; attendant and admin issue invoices and only admin cancels; plan limits shown only; revenue and active customers count `entregue` orders; 30-second poll stands. |
| [016](ADR-016-structured-address-and-invoice-payload.md) | Structured addresses and frozen invoice payloads | Customers and orders store a structured address. Invoices freeze their request body. The delivery fee becomes an invoice item by default. No CEP lookup in v1. |
| [017](ADR-017-data-access-hardening-and-status-rules.md) | Browser write lockdown, status move rules, and send retries | `authenticated` gets no writes. Status moves may skip forward and go back one step. Sends are not retried after a timeout. `MT_ALLOW_PRIVATE_HOSTS` is dev only. `orders.source` has `api`. Keys are looked up by hash. Test and live keys behave the same. |
| [018](ADR-018-tenant-composite-fks.md) | Tenant composite foreign keys, no deletes, API key use | Child keys carry `restaurant_id` into the parent. Orders, messages, conversations, customers, and history rows are never deleted; menu and stock items are archived. `mt.touch_api_key` records key use. |
| [019](ADR-019-english-paths.md) | English names for routes, folders, and files | Routes, folders, file names, and identifiers use English (`/new-order`, `menu-page.tsx`). UI text stays pt-BR; fiscal and legal terms stay Portuguese. |
| [020](ADR-020-finance-page-and-payment-status.md) | Finance page and payment status | `orders.paid_at` marks an order paid; `entregue` sets it when empty; staff mark it, only admin clears it. `/finance` lists paid orders with filters and totals and issues invoices one by one or in a batch. |
| [021](ADR-021-uatis-webhook-registration.md) | Register and use backend-uatis webhooks | Settings registers the backend-uatis webhook through its API, seals the returned secret, and checks `organization_id` on receipt. Amended by ADR-023 for the poll cadence and the public-URL rule. |
| [023](ADR-023-uatis-event-feed-push-and-pull.md) | One backend-uatis event log, read by push or pull | A webhook is `push` when `MT_PUBLIC_URL` is public, `pull` otherwise; the worker reads the cursor feed every 3 seconds (pull) or 5 minutes (push). One handler for both, deduplicated by event id. No tunnel. |
| [024](ADR-024-real-data-local-stack.md) | The local stack uses real data and the real sibling stacks | The seed holds accounts and configuration only; operational tables start empty. Marmita da Casa connects to the local web-nf (:3002) with its dev key; WhatsApp is connected in Configurações with an `obk_test_` admin key. `MT_UATIS_FAKE` and `MT_WEBNF_FAKE` default to 0. |
| [025](ADR-025-ai-order-assistant.md) | AI order assistant on WhatsApp | The worker runs a `claude-haiku-5-5` tool loop per inbound burst. The AI asks only for items, Retirada or Entrega, and the address; payment is "A definir". A server-rendered summary and a "sim" create the order. A plan quota of AI replies, with opt-in pay-by-usage overage and a hard cap. Off by default. |
| [026](ADR-026-order-status-messages.md) | Order status messages on WhatsApp | One automatic message kind per target status (`order_confirmed`, `order_preparing`, `order_ready`, `order_out_for_delivery`, `order_delivered`, `order_cancelled`), each with its own switch, text, and template. Forward moves and cancel only, once per order, pickup-only `order_ready`, the FR-117 window, same transaction as the move. |
| [027](ADR-027-ai-order-flow-fixes.md) | One summary, AI orders start as `aguardando`, every status move notifies | A turn that sent the summary sends no second text. `place_order` always creates `aguardando`, so a person confirms and `order_confirmed` goes out. `order_preparing` and `order_delivered` default to on (ADR-026 Amendment 2). Amendment 1: no AI text after an order that got an automatic message; opt-in auto-confirm of AI orders. |
| [028](ADR-028-status-flow-without-preparando.md) | Status flow without `preparando`; `entregue` becomes `finalizado` | Delivery `aguardando → confirmado → pronto → saiu → finalizado`; pickup skips `saiu`. `finalizado` is final, sets `delivered_at` and `paid_at`, and sends no message. `order_preparing` and `order_delivered` go away, leaving seven automatic messages. Migration 0025 renames existing rows. Amends ADR-017, ADR-026, ADR-027. |
| [029](ADR-029-ai-greeting.md) | The AI greets the customer, and asks a new customer's name | `welcome` is skipped when the AI will answer the message. The first AI reply asks a new customer's name, or greets a known customer by name and asks for the order. `update_cart` saves an empty customer name at once. |
| [030](ADR-030-public-menu-page.md) | Public menu page | `/m/{public_id}` shows the available menu without a session. `restaurants.public_id` is a fixed external id, so public links never show the internal restaurant id. A `security definer` function `mt.public_menu` returns only public columns; only `app_service` can call it. |
| [031](ADR-031-orders-from-the-public-menu.md) | Orders from the public menu | The customer orders on the public menu with name, phone, address, and payment method. `placePublicOrder` runs `createOrderInTx` with `source = menu`, always `aguardando`, behind business hours and rate limits. Phone-first layout. |
| [032](ADR-032-menu-orders-sent-by-whatsapp.md) | Menu orders are sent by WhatsApp | After the order, the page opens WhatsApp with the full order text, so the customer starts the conversation. The first inbound message from the order's phone links the open menu orders to the conversation, sends `order_received`, and pauses the AI. |
| [033](ADR-033-menu-order-drafts.md) | Menu order drafts | The checkout has no phone field. It saves a draft with a random reference and sends it in the WhatsApp text. The inbound message with the reference becomes the order, with the sender's phone and the conversation. |
| [034](ADR-034-periodic-jobs-do-not-back-off.md) | Periodic jobs do not back off | The timestamp poll and the feed read end on a transient failure, and the next tick tries again. A delayed retry no longer blocks polling for hours after a `backend-uatis` outage. |
| [035](ADR-035-auto-confirm-menu-orders.md) | Auto-confirm menu orders | A separate switch, `auto_confirm_menu_orders`, moves a menu order to `confirmado` when it is created, which sends `order_confirmed`. Off by default. |
| [036](ADR-036-order-received-text-for-confirmed-orders.md) | The order_received text for an order confirmed at creation | A fixed text by fulfillment ("Avisaremos quando seu pedido estiver pronto" / "for enviado") replaces "Em breve confirmaremos os detalhes" for orders confirmed when created. `createOrderInTx` takes `confirmOnCreate`. Amendment 1: such an order sends no `order_confirmed`. |
| [037](ADR-037-ai-uses-saved-address.md) | The AI uses the saved address | `update_cart` fills an empty delivery cart address from the customer's saved address. The AI does not ask for it again; the summary shows it, and the customer can change it. |
| [038](ADR-038-order-ticket-printing.md) | Order tickets print on a local thermal printer | A local `apps/print-agent` claims `print_jobs` through the public API and prints ESC/POS bytes with `lp -o raw`. One `order_ticket` job per accepted order when `auto_print_orders` is on. Lease 2 minutes, `failed` after 5 attempts. |
| [039](ADR-039-ai-continues-after-handback.md) | The AI continues the order after a hand-back | The AI reply of a hand-off run carries a `[sistema]` marker in the history. Hand-off reasons before it are closed, so after Retomar the AI reads the conversation and continues the order. |
| [040](ADR-040-ai-turn-wait-3-seconds.md) | The AI turn waits 3 seconds | `AI_TURN_DELAY_SECONDS` drops from 8 to 3. Later messages in a burst still get their own turn through the existing guards. |
| [041](ADR-041-production-uses-push-only.md) | Production uses push only | In production the api and the dashboard require a valid `MT_PUBLIC_URL`, "Ativar webhook" refuses pull, and the worker feed timer runs every 60 seconds. Development keeps pull. |
