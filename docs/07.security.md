# 07. Security

## Threat model (summary)

Assets:

* Customer personal data: names, phones, addresses, CPF/CNPJ, and message text.
* Third-party credentials per restaurant: the `backend-uatis` API key and webhook secret, the `web-nf` API key and webhook secret.
* The restaurant's outbound webhook secret and its Marmitop API keys.
* Tenant boundaries between restaurants.
* Order and invoice integrity: totals, status, and fiscal documents.

Main threats: cross-tenant reads, privilege escalation from `attendant` to `admin`, forged inbound webhooks, secret leaks through logs or backups, stolen API keys, tampered order totals, and SSRF through URLs that an admin enters. The full list is in "Threats and controls".

## Envelope encryption (ADR-012)

Each secret has its own random data key.

Encrypt (`SecretStore.put`):

1. Generate a 32-byte data key and a 12-byte IV with a CSPRNG.
2. Encrypt the plaintext with AES-256-GCM under the data key. Use the additional authenticated data (AAD) `secret:v1:{restaurant_id}:{secret_id}:{kind}`.
3. Wrap the data key with AES-256-GCM under `MT_KEK`, with a fresh 12-byte IV and the same AAD. Store `iv ‖ ciphertext ‖ tag` in `wrapped_key`.
4. Store `ciphertext ‖ tag`, `iv`, `wrapped_key`, `kek_version`, and `last4` in one `secrets` row.
5. Overwrite the data key buffer with zeros.

Decrypt (`SecretStore.get`) runs the steps in reverse. A GCM tag failure is an error, never a partial result.

The AAD binds a ciphertext to its row. An attacker with database write access cannot copy restaurant A's ciphertext into restaurant B's row and have B's integration use it: the tag check fails.

Rules:

* Plaintext exists only in memory, for one call, in `apps/api`, `apps/worker`, or the dashboard server. No cache across requests or jobs.
* No API response, Server Action result, or log line contains a plaintext secret. The UI shows "configured" and `last4`. `last4` is empty for a secret shorter than 12 characters, so a short value never shows whole.
* A secret is write-only from the UI. The admin replaces it. The admin never reads it back.
* Webhook secrets and the outbound signing secret are 32 random bytes, base62. Marmitop generates the outbound secret. The admin pastes the inbound ones from `backend-uatis` and `web-nf`.

KEK rotation:

1. Set `MT_KEK_PREVIOUS` to the old key, `MT_KEK` to the new key, and increment `MT_KEK_VERSION`. Deploy.
2. Run `scripts/rewrap-secrets.ts`. It unwraps each data key with the key that matches `kek_version`, wraps it again with the new key, and increments `kek_version`. Payloads do not change.
3. When no row has the old `kek_version`, unset `MT_KEK_PREVIOUS`.

The `SecretStore` port hides this design. A KMS or Supabase Vault can replace it with no caller change.

## API keys (ADR-009)

* Format: `mtk_live_<32 base62 chars>` or `mtk_test_<32 base62 chars>`, from 24 CSPRNG bytes or more.
* Stored: `hash` (hex SHA-256 of the full key) and `prefix` (`mtk_<env>_` plus the first 8 random characters). A fast hash with no salt is correct: the key is random, so a dictionary attack does not apply.
* Shown once, at creation. Only admins create and revoke keys.
* Authentication in `apps/api`:
  1. Read `Authorization: Bearer mtk_…`. Reject other formats with `401` before any database work.
  2. Hash the key. Call `mt.api_key_lookup(hash)`. This is the only lookup that runs before a restaurant context exists.
  3. Reject when no row matches or when `revoked_at` is set. The lookup is an index match on the hash, so the response time does not depend on how many characters of a guess are right.
  4. A `test` key and a `live` key behave the same: same data, same gateways. Only deployment config (`MT_UATIS_FAKE`, `MT_WEBNF_FAKE`) picks real or fake gateways (ADR-017, 06.api-spec.md). The key's `environment` goes to `audit_logs`.
  5. Call `mt.set_context(restaurant_id, 'api_key', null, key_id)`.
  6. Update `last_used_at` at most once per minute per key.
* A key acts as `attendant` (ADR-017, 05.data-model.md, `mt.actor_role()`). It cannot change settings, integrations, keys, menu, or stock.
* Every `401` and `403` has the same body shape and timing for "unknown key" and "revoked key".
* Rate limits per key: 600 reads and 120 writes per minute. Inbound webhook routes: 300 per minute per restaurant (06.api-spec.md).
* Implementation: `authenticateApiKey` in `packages/http/src/services/public-api/api-keys.ts`; the chain (key, rate limit, idempotency) in `apps/api/src/routes/public/middleware.ts`. A refused key logs the path only, never the key.

## Inbound webhook verification

Two routes in `apps/api`:

| Route | Header | Secret |
|---|---|---|
| `POST /v1/webhooks/uatis/{restaurant_id}` | `X-Uatis-Signature` | `integrations_whatsapp.webhook_secret_id` |
| `POST /v1/webhooks/web-nf/{restaurant_id}` | `X-NF-Signature` | `integrations_fiscal.webhook_secret_id` |

Both headers use one format: `t=<unix seconds>,v1=<hex HMAC-SHA256(secret, t + "." + raw_body)>`.

`packages/core` `verifySignature(header, rawBody, secret, now)` runs these steps in order:

1. Reject a body larger than 256 KB with `413`, before any parsing.
2. Read the raw body as bytes. Do not parse JSON first. A parse and re-serialize changes the bytes and breaks the HMAC.
3. Parse the header. Reject a missing `t`, a missing `v1`, or a `t` that is not an integer. Accept more than one `v1` value (secret rotation); pass when any one matches.
4. Reject when `|now − t| > 300` seconds.
5. Compute the HMAC over the exact string `t + "." + raw_body`.
6. Compare with `crypto.timingSafeEqual` on equal-length buffers. A length mismatch is a failure, decided without a byte-by-byte compare.
7. Only after a match, parse the JSON and validate it with the Zod schema.

The route does this:

* It sets the restaurant context from the path as `system`, reads the integration row, and decrypts the secret.
* An unknown restaurant, a missing integration, or a failed signature all return the same `401` body. The response does not say which check failed.
* After the signature, the backend-uatis route also requires `organization_id` to equal `integrations_whatsapp.uatis_organization_id` when that column is set, with the same `401` on a mismatch (ADR-021, FR-175).
* After the checks pass, it records the event id (`X-Uatis-Delivery`, or the body `id`) in `uatis_event_receipts` and skips an id seen before, then upserts by `external_id`. A replayed event changes nothing, whether it came by push or by the feed, because of the receipt, the idempotent upsert, and the forward-only status rank (ADR-023, FR-176).
* It returns `200` quickly and puts slow work on a queue.
* An unknown restaurant still runs the HMAC, against a random per-process dummy secret, so every failure path costs about the same.
* The per-restaurant rate limit (300 per minute, `rate_counters` class `webhook`) counts only requests that passed the signature check, so unsigned traffic cannot spend a restaurant's budget and block real deliveries. Floods of unsigned requests are an edge (load balancer) concern.
* Implementation: `packages/http/src/services/whatsapp/inbound-webhook.ts` (`receiveUatisWebhook`), route `apps/api/src/routes/webhooks/uatis.ts`.

Tests cover: a valid signature; a tampered body; a stale timestamp (301 s); a future timestamp (301 s); a wrong secret; a malformed header; two `v1` values with one valid.

Pull mode (ADR-023). The worker reads `GET /v1/webhooks/{id}/events` with the restaurant's API key through `safeFetch`. The trust comes from the TLS connection Marmitop opens to the base URL it stored, so no signature check applies, as for the timestamp poll. Feed events still pass the `organization_id` check and the same receipt dedupe. No inbound connection, no tunnel, and no relaxed SSRF guard are used anywhere. In production the backend-uatis base URL must be `https`: the URL rules refuse `http:` whenever `MT_ALLOW_PRIVATE_HOSTS` is off, and the flag is refused in production.

## Outbound webhook signing (ADR-009)

Each delivery sends these headers:

| Header | Value |
|---|---|
| `X-Marmitop-Signature` | `t=<unix>,v1=<hex HMAC-SHA256(secret, t + "." + body)>` |
| `X-Marmitop-Event` | for example `order.status_changed` |
| `X-Marmitop-Delivery` | `webhook_deliveries.id`. Receivers use it to drop duplicates. |
| `Content-Type` | `application/json` |
| `User-Agent` | `Marmitop-Webhooks/1` |

Rules:

* The body is `webhook_deliveries.payload`, serialized once at enqueue time and reused byte for byte on every attempt. Each attempt gets a fresh `t` and a fresh signature.
* Payloads carry ids and the fields an integrator needs. They never carry secrets, API keys, or the customer's CPF/CNPJ.
* The worker uses a 10-second timeout, follows no redirects, and reads at most 1 MiB of the response (the `safeFetch` cap). It never stores or logs the response body; `last_error` holds an allow-listed code such as `http_500` or `timeout`.
* A `2xx` is success. Any other status, a timeout, or a network error is a retry (ADR-007 backoff). A host the SSRF guard refuses is `exhausted` at once: nothing left the process.
* Implementation: `packages/http/src/adapters/webhook-sender.ts` (`SafeFetchWebhookSender`), `apps/worker/src/handlers/webhook-delivery.ts`.
* Receivers verify the same way as in "Inbound webhook verification". `packages/core` exports the verifier, and 06.api-spec.md documents it for integrators.

## SSRF guard

Admins enter three kinds of URL: the `backend-uatis` base URL, the `web-nf` base URL, and the outbound webhook URL. The worker and the dashboard server call these URLs with secrets attached. A hostile URL could point at internal services or cloud metadata. `packages/http` `safeFetch(url, opts)` is the only HTTP client for these calls.

In production (`MT_ALLOW_PRIVATE_HOSTS` unset, which is mandatory):

1. Accept `https:` only. Reject a URL with user info (`user:pass@`).
2. Resolve the host with DNS. Reject when **any** resolved address is in a blocked range:
   * IPv4: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`
   * IPv6: `::/128`, `::1/128`, `fc00::/7`, `fe80::/10`, `ff00::/8`, and IPv4-mapped forms of the IPv4 ranges (`::ffff:0:0/96`)
3. Connect to the address that was checked, not to a second DNS answer. This blocks DNS rebinding. The request keeps the original `Host` header and TLS SNI. `safeFetch` (`packages/http/src/adapters/safe-fetch.ts`) does the check inside the socket's `lookup` hook (`node:http`/`node:https`), so the connection uses exactly the checked address.
4. Follow no redirects. A `3xx` is a failure.
5. Apply the timeout and the response size limit.

The settings form runs steps 1 and 2 when the admin saves a URL, so the admin sees the error at once. The worker runs every step again on every call, because DNS can change after the save.

In local development, `backend-uatis` and `web-nf` run on `localhost`. `MT_ALLOW_PRIVATE_HOSTS=1` turns off step 2 and allows `http:` (ADR-017). The guard covers the admin-entered `backend-uatis` and `web-nf` base URLs as well as outbound webhook URLs. The worker and `apps/api` refuse to start when the flag is set and `MT_ENV=production`. Each logs a warning at start-up when the flag is set in any other environment. 11.operations.md lists the flag as forbidden in production.

## RLS and role enforcement (ADR-005)

Design in 05.data-model.md. Rules:

* Every tenant table has RLS enabled and forced (`force row level security`).
* `app_service` is `nobypassrls`. It is the only role that `apps/api`, `apps/worker`, and the dashboard server use.
* Every service transaction runs `mt.set_context(...)` first. `packages/db` `withRestaurantContext` is the only way to open one. A missing context reads as null, and every policy matches zero rows.
* The dashboard server resolves the restaurant and role from `mt.memberships_for_user(auth user id)` on every request. It never trusts a restaurant id or role from the client (ADR-004).
* **Two layers for roles.** The service layer checks the role first and returns a clear `403`. It is authoritative. The RLS write policies check `mt.can_write(...)` again. They are the backstop: a service that forgets its check still cannot write. `mt.actor_role()` reads the role from `restaurant_members` through `mt.set_context`, never from a value the code passes in.
* **Grants are part of the boundary.** `authenticated` holds `select` on `orders`, `messages`, and `conversations` only, for Realtime. It holds no write grant on any table (ADR-017). The browser holds the anon key and a session JWT, so any write grant would let it call PostgREST directly. The one exception is storage: a `storage.objects` policy lets admins upload to `menu-images`. Without this grant rule, a browser could call PostgREST with its session and change totals or status with no service check. `secrets` has no grant to `authenticated` or `anon` of any kind.
* **Composite tenant keys.** A foreign key check bypasses RLS, so every key between tenant tables includes `restaurant_id` on both sides (ADR-018). A child row can never reference another restaurant's parent, even from a buggy service or a DBA script.
* **No deletes on business records.** No role deletes orders, order items, invoices, messages, conversations, customers, or history rows in v1 (ADR-018). Menu and stock items are archived.
* **Triggers guard invariants that RLS cannot express:** order status transitions, the order subtotal, stock balances, the last admin of a restaurant, the secret kind behind each `*_secret_id`, and admin-only invoice cancellation.
* Every `security definer` function sets `search_path = pg_catalog, pg_temp`, uses schema-qualified names, is revoked from `public`, and is granted only to its callers. Migrations run as `postgres`, which owns them.
* Isolation tests: for every tenant table, seed restaurants A and B. Assert that a context for A reads zero rows of B, on the service path and (for the three Realtime tables) on the user path. Assert that an `attendant` context cannot write each admin-only table. Assert that `authenticated` cannot insert, update, or delete any table through PostgREST.

## Session authentication

* Supabase Auth, email and password. The dashboard middleware redirects any request without a valid session to `/login`.
* The middleware verifies the JWT in-process. HS256 tokens use `SUPABASE_JWT_SECRET`. ES256 and RS256 tokens use `SUPABASE_JWT_JWKS`. The algorithm is pinned to the one the header names. `none` is rejected. (Same rules as web-nf 07.security.md.)
* Server Actions call `getUser()` before a write, so a revoked session cannot write.
* The `next` parameter on `/login` accepts a same-origin path only. `//host` and `/\host` are rejected (open-redirect guard).
* Cookies are `HttpOnly`, `Secure`, `SameSite=Lax`.
* Server Actions rely on the Next.js origin check for CSRF. No route handler accepts a cookie-authenticated `POST` without that check.
* Login attempts are rate-limited by Supabase Auth.

## Audit logs

`audit_logs` is append-only (05.data-model.md). Each row names the actor (`user`, `api_key`, or `system`), the action, the entity, and a redacted `context`. Admins read it in Settings.

Audited actions:

| Area | Actions |
|---|---|
| Members | `member.added`, `member.role_changed`, `member.removed` |
| Restaurant | `restaurant.updated`, `settings.updated`, `business_hours.updated`, `automatic_message.updated` |
| Integrations | `integration.whatsapp.configured`, `integration.whatsapp.disconnected`, `integration.fiscal.configured`, `integration.fiscal.disconnected`, `secret.rotated` |
| API keys | `api_key.created`, `api_key.revoked` |
| Webhooks | `webhook_endpoint.created`, `webhook_endpoint.updated`, `webhook_endpoint.secret_rotated`, `webhook_endpoint.deleted`, `webhook_delivery.exhausted` |
| Orders | `order.cancelled` (with reason). Other status changes are in `order_status_history`, so they are not audited twice. |
| Invoices | `invoice.requested`, `invoice.cancel_requested`, `invoice.authorized`, `invoice.rejected` |
| Menu | `menu_item.price_changed`, `menu_item.deleted` |
| Stock | none. `stock_movements` is the ledger. |
| Customers | `customer.deleted` |

`context` holds ids, old and new values of non-secret fields, and the request id. It never holds a secret, a full API key, a message body, or a CPF/CNPJ. For a secret change it holds `kind` and `last4` only.

## Logging and redaction

* Logs are structured JSON (pino in the worker and `apps/api`). Each line carries `request_id` or `job_id`, `restaurant_id`, and `actor_type`.
* A redaction list in `packages/http` removes these keys at any depth: `authorization`, `cookie`, `set-cookie`, `x-uatis-signature`, `x-nf-signature`, `x-marmitop-signature`, `password`, `secret`, `api_key`, `apiKey`, `key`, `token`, `ciphertext`, `wrapped_key`, `iv`, `cpf_cnpj`, `body` (message text), `payload`.
* Request and response bodies are never logged. Webhook routes log the event type, the external id, and the result.
* Errors from `backend-uatis` and `web-nf` are logged as status code plus error code. Their message text is stored only when it matches an allow-list.
* Phone numbers in logs are masked to the last four digits.
* A unit test feeds a log line with each sensitive key through the logger and asserts the output does not contain the value.

## Transport

* All public endpoints use HTTPS, with HSTS at the edge.
* Calls to `backend-uatis` and `web-nf` use HTTPS in production, through `safeFetch`.
* The database connection uses TLS (`sslmode=require`) outside local development.

## Threats and controls

| # | Threat | Control |
|---|---|---|
| T1 | A user reads another restaurant's data | RLS on every table; context from `restaurant_members`, never the client; isolation tests |
| T2 | An attendant performs an admin action | Service role check; RLS `mt.can_write('admin')`; navigation hides items |
| T3 | A browser changes totals or status through PostgREST | No write grant to `authenticated`; transition and subtotal triggers |
| T4 | Server code forgets the restaurant filter | `app_service` is `nobypassrls`; a missing context returns zero rows |
| T5 | A forged inbound webhook | HMAC-SHA256 over `t.body`, constant-time compare, 5-minute window, same `401` for every failure |
| T6 | A replayed inbound webhook | 5-minute window; idempotent upsert by `external_id`; status only moves forward |
| T7 | A secret leaks through logs | Redaction list; no body logging; test on the logger |
| T8 | A secret leaks through a database dump | Envelope encryption; KEK outside the database; AAD binds ciphertext to its row |
| T9 | A stolen API key | Hash-only storage; prefix display; revocation on the next request; rate limit; key acts as `attendant` only |
| T10 | SSRF through an admin-entered URL | `safeFetch`: HTTPS, DNS check of every address, pinned connect, no redirects, timeout |
| T11 | An outbound webhook receiver is spoofed | `X-Marmitop-Signature`; receivers verify with the published verifier |
| T12 | A duplicate WhatsApp message to a customer | Outbound jobs are not retried after an ambiguous failure; see "Open risks" |
| T13 | A duplicate invoice in web-nf | `Idempotency-Key = order_invoices.id`; one live invoice per order (partial unique index) |
| T14 | Cross-tenant ciphertext swap | GCM AAD with `restaurant_id` and `secret_id`; trigger checks secret kind; composite foreign key checks the owner (ADR-018) |
| T15 | A public menu image exposes data | Bucket holds menu images only; write limited to admins by path; type and size limits |
| T16 | Open redirect after login | Same-origin `next` path only |
| T17 | Session theft | `HttpOnly` `Secure` cookies; `getUser()` before writes |
| T18 | The last admin removes themselves | Trigger on `restaurant_members` |
| T19 | Realtime leaks events across tenants | `authenticated` select policy by membership; no deletes on published tables |
| T20 | Webhook body too large (denial of service) | 256 KB limit before parsing |
| T21 | A service links a row to another restaurant's parent | Composite tenant foreign keys (ADR-018); meta-test on every key between tenant tables |

## Open risks

* **Duplicate outbound sends.** `POST /v1/messages` on `backend-uatis` accepts no idempotency key. When the worker times out after `backend-uatis` accepted a message, a retry sends the message twice. v1 retries only on a connection failure before the request is sent, or on a `5xx` with no body. A timeout marks the message `failed` with `error_code = 'ambiguous'` and the attendant decides. The fix belongs in `backend-uatis`: accept an `Idempotency-Key` header.
* **Late commits behind the feed cursor.** The backend-uatis feed returns rows older than 2 seconds. A backend-uatis transaction that runs longer can commit behind a cursor Marmitop already stored. In push mode the push delivers it. In pull mode the 10-minute timestamp poll recovers inbound messages; a late status update is lost until the next one (ADR-023).
* **Event latency in pull mode.** Up to `MT_UATIS_PULL_SECONDS` (3 seconds) plus the backend-uatis 2-second settle window and the job time (ADR-023). Push mode is about one second.
* **One KEK for all tenants.** A leaked worker environment exposes every restaurant's credentials. The upgrade is a KMS behind `SecretStore`.
