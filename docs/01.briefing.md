# 01. Briefing

## Problem

A small restaurant that sells marmitas (packed meals) runs its operation through scattered tools. Customers write on WhatsApp. Staff copy each order by hand into a notebook or a spreadsheet. Stock lives in someone's head. Revenue is a guess at the end of the month. Invoices are a separate chore at the accountant's office.

The results are lost messages, wrong orders, no view of what sells, and fiscal risk. Each tool solves one problem and ignores the others.

The current repository holds a Next.js dashboard prototype ("MarmitaChat"). It shows the right screens, but every screen reads mock data from `lib/marmita-data.ts`. Nothing is saved. No user can log in. No message reaches a real customer.

## What we build

**Marmitop** is a multi-tenant SaaS for restaurant managers. One web platform covers sales, finance, communication, orders, and stock.

* Messages and orders live in one place. A customer writes on WhatsApp. The attendant replies in the dashboard and creates the order from the chat.
* WhatsApp goes through `backend-uatis`, a sibling project that owns the WhatsApp Business Cloud API (ADR-002).
* Invoices go through `web-nf`, a sibling project that talks to the tax authority (ADR-003). The attendant issues an NFC-e or NFe from the order and reads the result, the XML, and the PDF there.
* Data lives in Supabase (Postgres, Auth, Realtime, Storage) with row-level security (ADR-005).
* The existing UI is the starting point. It moves to `apps/dashboard` without visual change and gets real data (ADR-001, ADR-004).

## Users

* **Restaurant admin** (owner or manager). Sees everything: menu, stock, reports, settings, integrations, and invoices. Configures the restaurant, connects WhatsApp and the fiscal service, and reads the numbers.
* **Attendant** (counter or phone staff). Uses messages, orders, new order, and contacts. Cannot open menu, stock, reports, or settings.
* **End customer on WhatsApp.** Never logs in. Writes to the restaurant number, receives replies and automatic messages, and gets the order status through the chat.
* **Integrator.** A developer who connects another system (a POS, a delivery marketplace, an ERP) through the public API with an API key and receives outbound webhooks.

## Goals

1. One screen set to run the day: conversations, orders board, new order, contacts, menu, stock, reports, settings.
2. A WhatsApp conversation becomes an order in a few clicks, and the order stays linked to the chat.
3. An order moves through a fixed status flow. Every change is recorded with who and when.
4. The server owns the rules: order total, status transitions, business hours, automatic messages. The browser never decides them.
5. Issue and track invoices from the order, through `web-nf`.
6. Strict tenant isolation. One restaurant never reads another restaurant's data.
7. Open to integration: a small public API and signed outbound webhooks.
8. Ready for billing: usage metering and plan screens behind an interface, with no payment provider yet (ADR-008).

## Success criteria (definition of done)

The goal fixes six criteria. Marmitop meets v1 when all six hold.

1. The scope document (this file and 02) and the data model (05) exist and match the built system.
2. A restaurant can complete this path: log in → configure profile, hours, and automatic messages → connect a WhatsApp number → register menu items → receive a customer message → reply from the dashboard → create the order from the chat → move it through the board until `entregue` → see it in reports. (FR-001, FR-083, FR-084, FR-085, FR-051, FR-010–019, FR-020–029, FR-070–079)
3. A counter or phone order can be created from New order with customer, items, sizes, delivery or pickup, and payment. It appears on the board in real time. (FR-030–039, FR-027)
4. Every dashboard screen reads and writes real data. No mock data from `lib/marmita-data.ts` remains in use. (NFR-063)
5. Tests pass for: order total calculation, status transitions and history, business-hours logic, WhatsApp webhook signature validation, automatic message triggers, report aggregations, and outbound webhook signing. (NFR-050)
6. Each phase ends with a short report in `docs/reports/`: what was done, what was verified, and what risk remains. (09.plan.md)

Because the real WhatsApp provider may not deliver webhooks yet (ADR-002), the path in criterion 2 runs in development with `FakeGateway` and the "Simulate customer message" control.

## Out of scope (v1)

* Payment collection. We meter usage and show plan and invoice-history screens. We charge no one (ADR-008).
* NFSe for orders. Prepared meals are goods, so the order flow issues NFC-e or NFe only (ADR-003). The municipality-template system and any backoffice from `web-nf` do not exist in Marmitop (ADR-013).
* Calling the Meta Cloud API directly. Marmitop holds no Meta credentials (ADR-002).
* Media messages (images, audio, documents, location) and WhatsApp templates. v1 sends and shows text.
* Several restaurants per user in the UI. The schema allows it. The v1 UI assumes one (ADR-005).
* Online ordering pages, delivery-courier tracking, maps, and route planning.
* Payment-gateway checkout for customers. The payment method is a label on the order.
* Recipes, automatic stock deduction from orders, and supplier purchasing. Stock changes only through movements.
* More than one outbound webhook URL per restaurant (ADR-009).
* Chatbot or AI replies. The "Regras de resposta" toggles in the prototype leave the UI.
* Mobile apps.
* Fiscal advice. Marmitop transports data. The restaurant owns tax content (NCM, CFOP, CSOSN, CST).

## Constraints that shape the design

* Fixed stack: Turborepo with Bun workspaces, Next.js (App Router, Turbopack), shadcn/ui, Hono, Supabase. No Redis and no external queue: pgmq and pg_cron run the jobs (ADR-007).
* Scope `@mt/*`. Apps: `dashboard`, `api`, `worker`. No app imports another app (ADR-001).
* Money is `bigint` cents (ADR-006). Timestamps are `timestamptz`.
* Third-party credentials are encrypted per restaurant (ADR-012).
* Every external dependency sits behind a port with a fake for tests: `WhatsAppGateway`, `InvoiceGateway`, `BillingProvider`.
* Spec first. Code traces to a numbered requirement. When reality forces a change, the spec changes first.
