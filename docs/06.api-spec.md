# 06. API specification

One HTTP API: `apps/api` (Hono, JSON, versioned under `/v1`). It serves three callers: integrators (API key), `backend-uatis` (inbound webhook), and `web-nf` (inbound webhook). The dashboard does not call this process. It reads and writes the same data through `@mt/http` services in process (ADR-004). Internal Server Actions are listed in Appendix A.

Base URL: `https://api.<product-host>/v1`. Local: `http://localhost:3101/v1`.

The OpenAPI file `06.openapi.yaml` sits next to this document. It is written from the schemas in `packages/schemas`. If the two disagree, the schemas win and this file gets fixed.

Requirements covered: FR-140–149 (public API, outbound webhooks), FR-100–119 and FR-120–139 (inbound webhooks), NFR security and rate-limit items.

## Authentication (FR-140)

| Route group | Credential |
|---|---|
| `/v1/orders`, `/v1/customers`, `/v1/menu`, `/v1/messages` | `Authorization: Bearer mtk_live_<base62>` or `mtk_test_<base62>` |
| `/v1/webhooks/uatis/{restaurant_id}` | `X-Uatis-Signature` |
| `/v1/webhooks/web-nf/{restaurant_id}` | `X-NF-Signature` |
| `/v1/health` | none |

API keys come from Settings → API keys (admin only). The server stores a SHA-256 hash and a display prefix. The full key shows once at creation (ADR-009). Lookup is by the unique SHA-256 hash of the presented key (`mt.api_key_lookup`, ADR-017). There is no prefix lookup step. A revoked key returns `401 unauthorized`. A key acts on one restaurant. A request for another restaurant's resource returns `404 not_found`. The API never confirms that a foreign id exists.

`mtk_test_` and `mtk_live_` keys behave the same: they reach the same restaurant data and the same gateways. Deployment config alone picks real or fake gateways (`MT_UATIS_FAKE`, `MT_WEBNF_FAKE`, ADR-017). The key's `environment` is recorded in `audit_logs`. An API key acts with the `attendant` role.

## Error format

Every error uses one envelope:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "The request body is invalid.",
    "details": [
      { "path": "items[0].menu_item_id", "code": "item_unavailable", "message": "Item is not offered on this weekday." }
    ]
  }
}
```

`details` is always present; it is `[]` when no field is at fault. `details[].path` is relative to the request body root, in the body's snake_case names (a header problem names the header, for example `Idempotency-Key`). Codes are `unauthorized`, `forbidden`, `not_found`, `validation_failed`, `conflict`, `idempotency_conflict`, `idempotency_in_progress`, `rate_limited`, `signature_invalid`, `invalid_status_transition`, `item_unavailable`, `whatsapp_not_configured`, `whatsapp_disconnected`, `outside_service_window`, `upstream_error`, `internal_error`. The table in `04.architecture.md` gives the HTTP status for each code.

## Pagination

Cursor-based: `?limit=50&cursor=<opaque>`. Default `limit` is 50. Maximum is 100. List responses use one envelope:

```json
{ "data": [], "next_cursor": "eyJpZCI6Ii4uLiJ9" }
```

`next_cursor` is `null` on the last page. Lists sort by `created_at` descending, then `id`.

## Idempotency (FR-141)

`POST` routes under `/v1/orders`, `/v1/customers`, and `/v1/messages` accept `Idempotency-Key` (1 to 255 characters; otherwise `422 validation_failed`). The key is scoped per restaurant. Keys expire after 30 days. The body hash covers the method, the path, and the raw body bytes.

The API claims the key before the request runs, in its own transaction (an `in_progress` row in `idempotency_records`, migration 0016). Two requests with one key therefore never both run:

| The claim finds | Answer |
|---|---|
| nothing | the request runs |
| `completed`, same body hash | the stored response, with `Idempotency-Replayed: true` |
| any row, another body hash | `409 idempotency_conflict` |
| `in_progress`, same body hash | `409 idempotency_in_progress` with `Retry-After: 1` |
| `in_progress` older than 60 seconds | the claim is taken over and the request runs |

A `2xx` stores the response and marks the row `completed`. Any other answer, or an error, deletes the claim, so the client can retry with the same key (for example after `422 outside_service_window` or a `5xx`). If storing a `2xx` response fails, the claim stays and is taken over after 60 seconds.

## Rate limits (FR-142)

Fixed-window counters per API key per minute, stored in Postgres so the limit holds across instances.

| Class | Routes | Default limit |
|---|---|---|
| read | all `GET` | 600 per minute |
| write | all `POST` and `PATCH` | 120 per minute |

Every response of an API-key route, success or error, carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (unix seconds). The order is: API key, rate limit, idempotency, route. Over the limit, the API returns `429 rate_limited` with `Retry-After` in seconds. Inbound webhook routes are not counted against a key. They get a fixed limit of 300 per minute per `restaurant_id`.

### Orders (FR-020–029, FR-143)

| Route | Method | Notes |
|---|---|---|

| `/v1/orders/{id}` | GET | Returns the order with `items` and `status_history`. `{id}` is the uuid or the code (`ORD-012`). |
| `/v1/orders` | POST | Creates an order. Idempotent. The server computes all totals (ADR-006). |
| `/v1/orders/{id}` | PATCH | Changes `status` only. Writes `order_status_history`. |

Create body:

```json
{
  "customer_id": "uuid",
  "fulfillment": "delivery",
  "cep": "01310100",
  "logradouro": "Rua das Flores",
  "numero": "120",
  "complemento": null,
  "bairro": "Centro",
  "cidade": "São Paulo",
  "uf": "SP",
  "codigo_municipio": "3550308",
  "payment_method": "pix",
  "change_for_cents": null,
  "notes": "Sem cebola",
  "items": [
    { "menu_item_id": "uuid", "size_id": "uuid", "qty": 2, "notes": null }

```

Rules:

* `source` is set to `api` for API calls. The client cannot send it (ADR-017).
* The client sends no prices. The server loads current prices and writes a snapshot in `order_items`.
* `logradouro` and `bairro` are required when `fulfillment` is `delivery`. Omitted address fields are copied from the customer. `cidade`, `uf`, and `codigo_municipio` then default to the restaurant's values (ADR-016). The API does not look up a CEP.
* `change_for_cents` applies only to `payment_method: "dinheiro"` and must be at least `total_cents`.
* An unavailable item, or an item not offered on today's weekday, returns `422 item_unavailable`.

### Menu (FR-050–059)

`GET /v1/menu` lists items. Filters: `kind` (`meal` or `drink`), `available` (`true` or `false`), `weekday` (0–6), `cursor`, `limit`. The API is read-only for menu data in v1. Each item has `id`, `kind`, `name`, `description`, `category`, `price_cents`, `calories`, `volume`, `available`, `popular`, `available_weekdays`, `image_url`, and `sizes` (`[{ id, name, price_cents, position }]`). Fiscal overrides (`ncm`, `cfop`) are not exposed.

### Messages (FR-010–019, FR-143)

`POST /v1/messages` sends a text to a customer through WhatsApp. Idempotent.

```json
{ "customer_id": "uuid", "body": "Seu pedido saiu para entrega." }
```

The API inserts a `messages` row (`direction: "out"`, `status: "pending"`), enqueues a job, and returns `201`:

```json
{
  "id": "uuid",
  "conversation_id": "uuid",
  "customer_id": "uuid",
  "direction": "out",
  "body": "Seu pedido saiu para entrega.",
  "status": "pending",
  "order_id": null,
  "created_at": "2026-10-13T12:00:00Z"
}
```

Optional field `order_id` links the message to an order. Before it inserts a row, the service checks the 24-hour service window (ADR-014) from the customer's last inbound message. Outside the window it returns `422 outside_service_window` and stores nothing. Template sending is out of scope for this endpoint. A customer with no conversation has never written, so the window is closed. A restaurant without a connected WhatsApp integration is not refused here: an API key acts as `attendant` and cannot read `integrations_whatsapp` (admin only). The message is stored and the worker sets `failed` with `error_code = whatsapp_not_configured`. The worker sends later. The worker does not retry after a timeout or a 5xx, because `backend-uatis` has no idempotency key on send (ADR-017). It sets the status to `failed` with `error_code = ambiguous`. A refusal from `backend-uatis` that gets past the check also sets `failed`. The `message.received` webhook and the dashboard report it. `GET /v1/messages` is not part of v1.

## Inbound webhooks

Both routes verify the signature before any write. They return `200` on success, including for a replay of a known message. They return `401 signature_invalid` for a bad signature or a timestamp more than 300 seconds from the server clock. An unknown restaurant, a malformed restaurant id, a missing integration row, and a disconnected integration get the same `401` body as a bad signature (FR-118, 07.security.md): the response never reveals whether a restaurant exists. A body over 256 KB gets `413` before any check. After a valid signature, a body that is not JSON or not a valid event gets `422 validation_failed`, and more than 300 requests in a minute for one restaurant get `429 rate_limited` with `Retry-After`. The success body is `{ "received": true }`. Verification uses HMAC-SHA256 and a constant-time compare, with the secret decrypted from `secrets` (ADR-012).

### POST /v1/webhooks/uatis/{restaurant_id} (FR-100–119)

Sender: `backend-uatis` (its customer-webhook delivery, `docs/06.api-spec.md` there). Headers:

* `X-Uatis-Signature: t=<unix>,v1=<hex hmac-sha256(secret, "<t>.<raw body>")>`
* `X-Uatis-Event: message.created | message.updated | conversation.updated`
* `X-Uatis-Delivery: <delivery uuid>`

`message.created` and `message.updated` body:

```json
{
  "id": "delivery-uuid",
  "type": "message.created",
  "created_at": "2026-10-13T12:00:00Z",
  "organization_id": "uuid",
  "data": {
    "message": {
      "id": "uuid",
      "conversation_id": "uuid",
      "direction": "in",
      "content": { "type": "text", "text": { "body": "Oi" } },
      "status": { "state": "received" },
      "contact_address": "+5511999999999",
      "created_at": "2026-10-13T12:00:00Z"
    }
  }
}
```

`conversation.updated` carries `data.conversation` (`id`, `contact_id`, `organization_address`, `extra`, `updated_at`). Marmitop ignores it in v1 and returns `200`.

Handling:

| Event | Action |
|---|---|
| `message.created`, `direction: "in"` | Upsert customer by `contact_address`, conversation, and message (`external_id = data.message.id`). Unread count + 1. Run automatic messages. Emit `message.received`. |
| `message.created`, `direction: "out"` | A known `external_id` gets the status update below. An unknown one is ignored in v1: Marmitop stores the id of its own send only after `POST /v1/messages` returns, so the echo can arrive first, and storing it would duplicate the message. Messages sent from another tool therefore do not appear in Marmitop. |
| `message.updated` | Update `messages.status` by `external_id`. State mapping: `pending` → `pending`, `sent` → `sent`, `delivered` → `delivered`, `read` → `read`, `failed` → `failed`. `received` stays as is. |

Only text content is stored in v1. backend-uatis stores text as `content.text` (a string); its own spec shows `content.text.body`. Marmitop reads both (ADR-002 Amendment 2). A non-text message gets the body `[mídia não suportada]`. Rows with `direction: "internal"` (agent tool traffic) are skipped. The same rules apply to the reconciliation poll.

### POST /v1/webhooks/web-nf/{restaurant_id} (FR-120–139)

Sender: `web-nf` (its webhook delivery, `docs/06.api-spec.md` there). Headers:

* `X-NF-Signature: t=<unix>,v1=<hex hmac-sha256(secret, "<t>.<raw body>")>`
* `X-NF-Event: invoice.authorized | invoice.rejected | invoice.denied | invoice.failed | invoice.cancelled | event.authorized | event.rejected`
* `X-NF-Delivery: <delivery uuid>`

Body:

```json
{
  "id": "delivery uuid",
  "type": "invoice.authorized",
  "created_at": "2026-10-13T12:00:00Z",
  "data": {
    "invoice": {
      "id": "web-nf invoice uuid",
      "kind": "nfce",
      "status": "authorized",
      "numero": 1234,
      "chave_acesso": "42261001234567000189650010000012341000012349",
      "reference": "order_invoice uuid"
    }
  }
}
```

`event.authorized` and `event.rejected` deliveries also carry `data.event: { id, type, status }` (web-nf `apps/worker/src/pipeline/webhook-fanout.ts`). The body never carries `serie` or the error code and text.

Handling: find `order_invoices` by `external_id = data.invoice.id`. If no row matches, find it by `id = data.invoice.reference` with `external_id` still null, and store `external_id`: the delivery can arrive before the worker stores the id. Map the event to a status (`invoice.authorized` → `authorized`, `invoice.rejected` → `rejected`, `invoice.denied` → `denied`, `invoice.failed` → `failed`, `invoice.cancelled` → `cancelled`). Store `numero` and `chave_acesso`. The update follows the status rule of 08 section 6: a repeated delivery changes nothing, and a final status never moves back (FR-136). When the status moved to anything but `cancelled`, Marmitop queues an `mt_invoice_jobs` job with `op: poll`, because only `GET /v1/invoices/{id}` carries `serie` and the error code and text. `event.authorized` and `event.rejected` concern cancellation events: Marmitop queues the same poll and does not trust the event body for state. An unknown invoice id returns `200` (no retry storm) and writes an audit log. Then Marmitop emits `invoice.updated` (P7).

The Marmitop `reference` sent to web-nf is the `order_invoices.id`. It is also the `Idempotency-Key`.

## Outbound webhooks (FR-144–147)

The restaurant sets one URL in Settings → Webhook (ADR-009). The worker sends a `POST` with a JSON body and a 10-second timeout. It follows no redirects. In production it blocks private, loopback, and link-local hosts. A `2xx` response counts as delivered. Any other status, a timeout, or a network error retries at 1 m, 5 m, 30 m, 2 h, and 8 h, then the delivery status is `exhausted`. A host the SSRF guard refuses is `exhausted` at once, and so is a delivery whose endpoint is disabled. The attempt number comes from `webhook_deliveries.attempts`, so a job that the sweep re-enqueued keeps the schedule. Every attempt is recorded in `webhook_deliveries` (status, attempts, last status code, an allow-listed `last_error` such as `http_500` or `timeout`) and `job_attempts`.

Producers call `emitEvent(tx, restaurantId, type, data)` (`packages/http/src/services/webhooks/emit.ts`) inside their own transaction. It inserts one `pending` delivery for the endpoint when it is enabled and subscribed to `type`, and enqueues `mt_webhook_deliveries` in the same transaction. Emitters: `createOrder` (`order.created`), the status move (`order.status_changed`), `ingestInboundMessage` (`message.received`; webhook, poll, and dev simulation), and the invoice flow (`invoice.updated`).

Headers:

* `X-Marmitop-Signature: t=<unix>,v1=<hex hmac-sha256(secret, "<t>.<raw body>")>`
* `X-Marmitop-Event: order.created`
* `X-Marmitop-Delivery: <delivery uuid>`
* `User-Agent: Marmitop-Webhooks/1`

Receivers must verify the HMAC and reject a `t` more than 5 minutes old. This is the same scheme as backend-uatis and web-nf.

Envelope:

```json
{
  "id": "delivery uuid",
  "type": "order.created",
  "created_at": "2026-10-13T12:00:00Z",
  "restaurant_id": "uuid",
  "data": {}
}
```

| Event | `data` |
|---|---|
| `order.created` | `{ "order": <Order object> }` |
| `order.status_changed` | `{ "order_id", "code", "from_status", "to_status", "changed_at" }` |
| `message.received` | `{ "message": { "id", "conversation_id", "customer_id", "body", "created_at" }, "customer": { "id", "name", "phone" } }` |
| `invoice.updated` | `{ "invoice": { "id", "order_id", "kind", "status", "numero", "serie", "chave_acesso", "error_code", "error_message", "updated_at" } }` |

`invoice.updated` never contains XML or PDF URLs.
