# 11. Operations

## Deploy targets

| Component | Target | Notes |
|---|---|---|

| Environment | Purpose | Integrations |

## Local development

The Supabase CLI is the local environment. It runs Postgres, Auth, Storage, and Realtime in Docker, and applies `supabase/migrations/` plus `supabase/seed.sql` on every reset. The root `bun run dev` starts every app through turbo. Each app also starts alone (`bun run --cwd apps/dashboard dev`). Either way the CLI stack owns only the database and its adjacent services.

**Bootstrap:** `bun run dev:stack` (`bun scripts/local-dev.ts up`) runs, in order:

1. `supabase start` (skipped if already running; needs Docker Desktop or a compatible engine).
2. `supabase db reset` (migrations, then `supabase/seed.sql`).
3. Write each app's env file from `supabase status -o json` plus the fixed values in `scripts/dev-seed/constants.ts`.
4. Run `scripts/dev-seed/verify.ts`.
5. Print URLs, logins, and API keys.

`bun run db:reset` repeats steps 2–5 on a running stack. `bun run dev:stack:down` runs `supabase stop`. `bun run seed:generate` regenerates `supabase/seed.sql` from `scripts/dev-seed/generate.ts`. `bun run seed:verify` reruns the checks alone. The generator and `scripts/local-dev.ts` use Node and Bun built-ins only. `verify.ts` and `scripts/test-db.ts` (`bun run db:test`) use postgres.js through `packages/db`.

**Session tokens:** the local Auth service signs sessions with an ES256 key, not with the `JWT_SECRET` that `supabase status` reports. If `apps/api` verifies Supabase sessions, the bootstrap reads the public JWKS from `/auth/v1/.well-known/jwks.json` and writes it to `apps/api/.env`. A missing JWKS makes the bootstrap fail rather than write a broken file. The dashboard verifies sessions through Supabase JS and needs neither value.

**Ports:**

| Service | Port |
|---|---|
| dashboard | 3100 |
| api | 3101 |
| worker health | 8181 |
| Supabase API | 54421 |
| Postgres | 54422 |
| Studio | 54423 |

The ports do not collide with web-nf or backend-uatis, so all three stacks can run together.

**Credentials:** every seeded login, API key, and secret is a fixed, documented dev fixture, never a random value, and never reused outside this stack. `scripts/dev-seed/constants.ts` is the single source. Dev secrets are wrapped under a dev `MT_KEK` from the constants file.

**Seeded data (ADR-024):** the seed holds accounts and configuration only. It creates two restaurants, each with one `admin` and one `attendant`, their settings, business hours, automatic messages, and public API keys. Menu, stock, customers, conversations, orders, and invoices start empty and come only from use of the apps and the sibling stacks.

**Real sibling stacks (ADR-024):** `scripts/local-dev.ts` writes `MT_UATIS_FAKE=0` and `MT_WEBNF_FAKE=0`. Marmita da Casa (`qwe@qwe.com`) has a seeded fiscal integration with the local web-nf generation API (`http://127.0.0.1:3002`, homologação), using web-nf's own dev key. WhatsApp is not seeded, because `backend-uatis` has no seeded key that authenticates. To see the real flow:

1. Start `backend-uatis` and web-nf with their own dev commands. The local `backend-uatis` apps use its cloud Supabase project, not a local stack: real WhatsApp numbers, users, and messages exist only there.
2. Run `bun run db:reset`. Then start, or restart, `bun run dev`. The api and the worker read their env files only at start.
3. Create an `admin` API key in the `backend-uatis` cloud database. Either run `scripts/uatis/connect-marmitop.sql` in its Supabase SQL editor (set your e-mail first; it prints the key once, the `phone_number_id`, and the migration check), or sign in to the `backend-uatis` dashboard (`http://localhost:3300`) with your cloud user and create the key there.
4. Sign in to Marmitop as `qwe@qwe.com`. In Configurações → WhatsApp, save `http://127.0.0.1:3301`, the key, and the `phone_number_id`. Press "Salvar e testar", then "Ativar webhook". The panel shows "Ativo · Pull". The cloud database must have the `backend-uatis` migration `20261014120000_webhook_pull_mode`; without it, "Ativar webhook" fails and only the 30-second poll delivers.
5. Register a menu item, receive or create an order, and issue an invoice.

With a sibling down, sends, polls, and invoice issues fail, and the worker records each attempt in `job_attempts`. Sabor de Minas has no integration; connect both in Configurações.

**Simulating WhatsApp:** with `MT_UATIS_FAKE=1`, use the dev-only "Simulate customer message" control in Mensagens (ADR-002).

**Accepted limitations:**

* A send reaches a real phone. Use a test number you own. Outside the 24-hour service window, WhatsApp accepts only approved templates.
* The integration tests use database `mt_test` on the local stack's cluster (10.testing.md). It is separate from the dev database `postgres`, so a test run never changes seeded data, and `supabase db reset` never touches `mt_test`. `supabase stop --no-backup` deletes both; the harness recreates `mt_test` on the next run.
* After WhatsApp is connected, pg_cron enqueues a poll every 30 seconds. With `backend-uatis` down, each poll records a failed attempt.

## Configuration and secrets

Each app has an `.env.example` listing names only.

| App | Variables |
|---|---|
| `apps/dashboard` | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `DATABASE_URL`, `MT_KEK`, `SUPABASE_URL`, `SUPABASE_JWT_SECRET` or `SUPABASE_JWT_JWKS`, `MT_PUBLIC_URL`, `MT_ENV`, `MT_LOG_LEVEL`, `PORT`, `MT_UATIS_FAKE`, `MT_WEBNF_FAKE`, `MT_ALLOW_PRIVATE_HOSTS` (development only) |
| `apps/api` | `DATABASE_URL`, `MT_KEK`, `SUPABASE_URL`, `SUPABASE_JWT_SECRET` or `SUPABASE_JWT_JWKS`, `MT_PUBLIC_URL`, `MT_ENV`, `MT_LOG_LEVEL`, `PORT`, `MT_UATIS_FAKE`, `MT_WEBNF_FAKE`, `MT_ALLOW_PRIVATE_HOSTS` (development only) |
| `apps/worker` | `DATABASE_URL`, `MT_KEK`, `SUPABASE_URL`, `MT_ENV`, `MT_LOG_LEVEL`, `MT_WORKER_CONCURRENCY`, `WORKER_HEALTH_PORT`, `ANTHROPIC_API_KEY`, `MT_AI_MODEL`, `MT_AI_EFFORT`, `MT_UATIS_FAKE`, `MT_WEBNF_FAKE`, `MT_ALLOW_PRIVATE_HOSTS` (development only) |

The canonical list, with meanings, is the table in 04.architecture.md "Configuration". `MT_KEK_PREVIOUS` is set only during a KEK rotation. In production, `MT_ALLOW_PRIVATE_HOSTS`, `MT_UATIS_FAKE`, and `MT_WEBNF_FAKE` must be unset. The api and worker refuse to start when `MT_ALLOW_PRIVATE_HOSTS` is set and `MT_ENV=production` (ADR-017).

* `DATABASE_URL` connects as `app_service` (`nobypassrls`). Migrations use a separate admin URL that only the migration step holds.
* Platform secrets (`MT_KEK`, the `app_service` password, Supabase keys) live in the host's secret store (Fly secrets, Railway variables, Vercel env).
* Per-restaurant secrets (backend-uatis key and webhook secret, web-nf key and webhook secret, outbound webhook secret) live encrypted in the `secrets` table (ADR-012). They never appear in env files, logs, or API responses.
* The same `MT_KEK` value must reach the dashboard, API, and worker. A mismatch shows as decryption failures.
* `MT_PUBLIC_URL` is the public base URL of `apps/api`. The dashboard reads it when the admin presses "Ativar webhook" (ADR-021, ADR-023, FR-172), so the dashboard and the api must hold the same value. When it is an absolute `https` URL on port 443 (no port in the URL), with no user name, password, query, or fragment, and a host that is not `localhost`, a private name (`.local`, `.internal`, and so on), or a private, loopback, or link-local IP, the webhook is registered in **push** mode. Otherwise it is registered in **pull** mode. A path prefix is allowed; a trailing `/` is dropped. `MT_ALLOW_PRIVATE_HOSTS` does not change the choice.
* `MT_UATIS_PULL_SECONDS` (worker, default 3, from 1 to 60) is how often a restaurant in pull mode reads the backend-uatis event feed. Push mode reads it every 5 minutes to recover lost pushes.
* AI order assistant variables (worker only, ADR-025, FR-198): `ANTHROPIC_API_KEY` is a secret. Set it in the host's secret store. An empty value selects `ScriptedAssistantModel` with an empty script (fake mode), so no call leaves the process. In fake mode every AI turn fails on its first model call. Each AI-enabled conversation that gets a turn records one `ai.reply` usage row and is paused with reason `model`. Never run production with an empty key. `MT_AI_MODEL` defaults to `claude-haiku-5-5`. `MT_AI_EFFORT` defaults to `low`. The dashboard and `apps/api` never load these variables.
* In production the backend-uatis base URL must be `https` (ADR-023 security rule 2). The SSRF guard enforces it, because `MT_ALLOW_PRIVATE_HOSTS` is refused there.

### backend-uatis events in local development (pull mode)

No tunnel is needed, and none should be used (ADR-023). With `MT_PUBLIC_URL=http://localhost:3101`, "Ativar webhook" registers a **pull** webhook. The worker then reads `GET /v1/webhooks/{id}/events` every `MT_UATIS_PULL_SECONDS` seconds with the restaurant's API key. Marmitop makes outbound HTTPS calls only, the same path it uses to send messages.

1. Run backend-uatis with the event feed (its ADR for `webhooks.mode` and `/events`).
2. Check that `MT_UATIS_FAKE=0` (the default since ADR-024) is set in `apps/dashboard/.env.local` and `apps/worker/.env`. With `MT_UATIS_FAKE=1` each process has its own in-memory gateway, so the worker cannot see a webhook the dashboard registered: its first feed read gets `404`, `GET /v1/webhooks/{id}` answers 404 too, and the worker clears the webhook and goes back to the timestamp poll. Settings then shows "Não registrado" again. This is expected with the fake.
3. In Configurações → WhatsApp, save the backend-uatis URL, a dedicated `obk_test_` key with role `admin` (webhooks and the feed need it; a `member` key gets "A chave da API do Uatis precisa ser de administrador."), and the `phone_number_id`. Press "Ativar webhook". The panel shows "Ativo · Pull".
4. Send a WhatsApp message to the test number. It shows in Mensagens within a few seconds.

`bun apps/worker/e2e-uatis/replay-webhook.ts` posts a signed body in the exact backend-uatis push format to the local api, to check the push path without backend-uatis (10.testing.md).

## Migrations

SQL files live in `supabase/migrations/`, named `NNNN_name.sql`. One directory, three appliers, each with its own ledger:

| Applier | Environment | Ledger |
|---|---|---|
| Supabase CLI (`supabase db reset`) | local development | `supabase_migrations.schema_migrations` |
| Custom runner (`bun run --cwd packages/db migrate`) | staging, production | `public.schema_migrations` (sha256 checksum per file, advisory lock) |
| `scripts/test-db.ts` | integration-test harness | `public._mt_test_migrations` |

Rules:

* Forward-only. Never edit or rename an applied file. If a stored checksum no longer matches, the runner exits 2.
* Numbered, in order. Idempotent where possible (`if not exists`).
* RLS is enabled in the same migration that creates the table, never later (NFR-001). The meta-test in 10.testing.md fails otherwise.
* Production migration: run the runner against the production URL from a trusted shell, after staging ran the identical files.
* Deploy the migration before the code that reads it. A new column or table is added first, then used.
* The runner resolves the migrations directory from its own module path. A deploy artifact for the migration step must ship `supabase/migrations/` next to `packages/db/`.
* Post-migration check (staging and production): `select jobname, username, schedule from cron.job order by jobname;` returns the expected jobs with a single username.
* Per-environment provisioning outside migrations: set the `app_service` login password, grant it the roles it needs, and add `orders`, `messages`, and `conversations` to the `supabase_realtime` publication if the migration could not (ADR-004). Hosted projects also keep auth e-mail templates in the Supabase dashboard.

## pg_cron and pgmq

Queues (ADR-007): `mt_outbound_messages`, `mt_webhook_deliveries`, `mt_invoice_jobs`, `mt_sync`.

| Schedule | Job |
|---|---|
| every 30 seconds | enqueue a reconciliation poll on `mt_sync` for each connected restaurant (ADR-002). A restaurant with a registered backend-uatis webhook is skipped: it reads the event feed instead (ADR-023, FR-174). |
| every 10 minutes (inside the 30-second job) | the timestamp poll for restaurants in pull mode, a safety net for backend-uatis commits that land behind the feed cursor (ADR-023) |
| every `MT_UATIS_PULL_SECONDS` (worker timer, not pg_cron) | `mt.enqueue_uatis_feed_pulls`: a `uatis_feed_pull` job for each restaurant in pull mode, and every 5 minutes for push mode |
| daily | `mt.trim_uatis_event_receipts` deletes receipts older than 8 days |
| every minute | enqueue poll jobs for invoices still not final; re-queue jobs past their visibility timeout |
| daily | trims (see Backups and retention) |

Useful queries:

```sql
select * from pgmq.metrics_all();
select * from pgmq.metrics('mt_outbound_messages');
select * from cron.job order by jobname;
select * from cron.job_run_details order by start_time desc limit 20;
select * from pgmq.read('mt_sync', 0, 10);   -- peek without consuming (vt 0)
```

Jobs are idempotent and delivery is at least once. A worker restart is always safe. Retries back off at 1m, 5m, 30m, 2h, and 8h. After the last attempt the job is archived as failed and its `job_attempts` row says why.

## Observability

* Structured JSON logs to stdout; the host collects them. Fields: `ts`, `level`, `service`, `req_id`, `restaurant_id`, `route`, `status`, `latency_ms`, and for jobs `queue`, `job_id`, `attempt`. Never secret material, message bodies, or full phone numbers.
* Health: `/v1/health` on `apps/api`; the worker serves `/health` on 8181 with queue depth and last poll age.
* Metrics come from the database, with no separate stack in v1: `job_attempts` (retries and failures per queue), `webhook_deliveries` (status, attempts, `last_status_code`, `next_attempt_at`), `order_invoices` (status and error), `messages` (`failed` status), `usage_events`.
* Audit: `audit_logs` records settings, member, API key, and integration changes with actor and restaurant.
* Host-level alerts (v1): worker health failing; queue depth growing for 15 minutes; `failed` messages or `webhook_deliveries` rising; API error rate.

## Runbooks

### WhatsApp messages are not arriving

1. In Configurações → WhatsApp check the integration status. If it is `disconnected`, fix the credentials first.
2. Check the webhook panel in Configurações → WhatsApp: the state, the mode, the last push, the last feed read, and the last five backend-uatis attempts. "Não registrado" means only the 30-second timestamp poll delivers; press "Ativar webhook". In pull mode, a "Última leitura" that does not move means the worker is down or the feed call fails: read `job_attempts` for `mt_sync` rows with op `uatis_feed_pull`. Push attempts that fail with `ssrf_blocked` mean `MT_PUBLIC_URL` resolves to a private address.
3. If push attempts reach `apps/api` and fail, look at what it answered. `401` means the signature or the organization check failed: the stored secret differs from backend-uatis, the API key now belongs to another organization, or the server clock is off by more than 5 minutes. Press "Ativar webhook" again to register a new webhook and secret. The feed recovers the missed events either way.
4. Check the poll cursor: `select last_sync_cursor, status from integrations_whatsapp where restaurant_id = '<id>';`. Then `pgmq.metrics('mt_sync')` and `job_attempts` for recent `mt_sync` rows. A cursor that does not move with a healthy queue means the backend-uatis call fails; read the attempt's error.
5. If the cursor is stuck on a bad record, set it back to a value before the gap. Upserts are keyed by `external_id`, so a replay creates no duplicates.
6. Confirm the fix: send a test message and watch the conversation appear within one poll interval.

### Outbound messages stay `pending` or `failed`

1. `select status, count(*) from messages where direction = 'out' group by 1;`
2. Check `pgmq.metrics('mt_outbound_messages')` and the worker `/health`.
3. Read `job_attempts` for the cause (bad key, backend-uatis down, rejected number). Fix, then re-send from the dashboard.
4. A message `failed` with `error_code = ambiguous` may have reached the customer, because `backend-uatis` has no idempotency key on send and the worker does not retry (ADR-017). Check the conversation in `backend-uatis` before you resend.
5. A message `failed` with `error_code = outside_service_window` is outside the 24-hour window (ADR-014). The customer must write first, or the restaurant must configure an approved `order_received` template.

### Invoice stuck in `processing`

1. Find it: `select id, order_id, status, external_id, updated_at, error_code from order_invoices where status in ('queued','processing') and updated_at < now() - interval '15 minutes';`
2. Check `mt_invoice_jobs` and `job_attempts`. A queued job with no worker means the worker is down: restart it.
3. If `external_id` is set, ask web-nf for the truth: `GET /v1/invoices/{external_id}` with the restaurant's key. The poll job does this, so a stuck row usually means the poll failed. Fix the key or URL and wait for the next poll, or update the row from the web-nf answer.
4. If `external_id` is empty, the first call never succeeded. Re-enqueue the job. The `Idempotency-Key` (the `order_invoices.id`) prevents a second invoice.
5. If web-nf says `rejected`, show the mapped message in the UI (08.fiscal-mapping.md) and let the attendant correct the order or the fiscal data and issue again.

### Webhook endpoint failing (outbound)

1. `select event, status, attempts, last_status_code, next_attempt_at from webhook_deliveries where endpoint_id = '<id>' order by next_attempt_at desc limit 20;`
2. Read the code. `4xx` means the receiver rejects it: check the URL and signature verification on their side (header `X-Marmitop-Signature`, formula in ADR-009). `5xx` or a timeout means their server is down, and retries continue on the schedule. A refused host in production means the SSRF guard blocked a private address.
3. After the fifth failed attempt the delivery stays `failed`. When the receiver is fixed, re-enqueue it from the dashboard or with `update webhook_deliveries set status = 'pending', attempts = 0, next_attempt_at = now() where id = '<id>'`, plus the matching queue message.
4. To rotate the endpoint secret, generate a new one in settings, give it to the receiver, then save.

### KEK rotation

1. Generate a new 32-byte `MT_KEK` (base64).
2. Re-wrap every data key under the new KEK. No packaged command exists yet: write a one-off script against the `secrets` table using the envelope layout in `packages/http/src/secret-store.ts`. Unwrap each `wrapped_key` with the old KEK and wrap it with the new one. `ciphertext` and `iv` stay untouched (ADR-012).
3. Test the script against staging first, then take a database snapshot of production.
4. Set the new `MT_KEK` on the dashboard server, `apps/api`, and `apps/worker`, remove the old value, and restart all three together.
5. Verify: open Configurações → WhatsApp (shows "configured"), send a test message, and check there are no decryption errors in the logs.

### Worker stuck or crashed

1. Check worker `/health` and host logs.
2. `select * from pgmq.metrics_all();` and `cron.job_run_details`.
3. Restart the worker. Jobs past their visibility timeout return to the queue. At-least-once delivery and idempotent jobs make this safe (NFR-022).

### Restoring backups

1. Pick the recovery point (Supabase daily backup, or point-in-time recovery if enabled).
2. Restore into a new project first, never over production. Check row counts of `orders`, `messages`, `customers`, and `secrets`.
3. `secrets` are encrypted, so the restored data is useful only with the same `MT_KEK`. Keep the KEK in the host secret store with its own backup.
4. Re-run any forward migrations newer than the backup. Check `cron.job` and the `supabase_realtime` publication, which may need re-creating.
5. Point the apps at the restored database (`DATABASE_URL`), restart them, and let the reconciliation poll fill the gap: it re-reads backend-uatis messages from the stored cursor, and the invoice poll refreshes web-nf status. Messages sent from the dashboard after the restore point and lost with it are the real loss; tell the restaurants.
6. Record the incident in `docs/reports/`.

## Order ticket printer (ADR-038, FR-250–254)

The print agent runs on the counter computer that has the USB thermal printer. It needs Bun and a checkout of this repository.

1. Connect the printer by USB. Run `lpinfo -v`. Find the line `direct usb://...` for the printer, for example `usb://Printer/POS-80?location=2200000`.
2. Add a driverless CUPS queue. Do not pass `-m raw`, because macOS refuses it:

   ```bash
   lpadmin -p Elgin_i8 -E -v 'usb://Printer/POS-80?location=2200000' -D 'Elgin i8 (Marmitop)' -o printer-is-shared=false
   ```

3. In Configurações → "WhatsApp, webhook e API", create an API key for the restaurant. In Configurações → Pedidos, turn on "Imprimir comanda automaticamente".
4. Write `apps/print-agent/.env` from `apps/print-agent/.env.example`: `MT_API_URL`, `MT_API_KEY`, and `MT_PRINTER` (the queue name from step 2).
5. Run `bun run --cwd apps/print-agent start`. To print a sample ticket without the API, run `bun run --cwd apps/print-agent test-print`.

6. To start the agent at login and restart it if it stops, run `bun run --cwd apps/print-agent launchd:install`. It writes `~/Library/LaunchAgents/com.marmitop.print-agent.plist` and loads it. The log is `~/Library/Logs/Marmitop/print-agent.log`. Run `launchd:install` again after you move the repository or change `.env`. Run `launchd:uninstall` to remove it.

The agent keeps the ids of printed jobs in `~/.marmitop/printed-jobs.json` (`MT_PRINT_STATE`). A job that printed, but whose result did not reach the API, comes back after the 2-minute lease. The agent then reports it and does not print it again (FR-254).

### Tickets do not print

1. Run `lpstat -p Elgin_i8`. The queue must be `idle` or `printing`, not `disabled`. Run `cupsenable Elgin_i8` to enable it again.
2. Read the agent log (`~/Library/Logs/Marmitop/print-agent.log`). `claim failed` means the API or the key is wrong. `print failed` means CUPS refused the job.
3. A job with `status = failed` in `print_jobs` stopped after 5 attempts. Set it back to `pending` with `attempts = 0` to print it again.

## Backups and retention

* Database: Supabase automated backups (daily). Verify a restore every quarter.
* `job_attempts`, `webhook_deliveries`, `audit_logs`, and `usage_events` are trimmed by a daily pg_cron job; the exact windows are set in the migration that creates the job (default: 90 days for attempts and deliveries, 1 year for audit logs).
* Orders, messages, customers, and `order_invoices` are never trimmed automatically.
* Fiscal XML and PDF live in web-nf, not in Marmitop. Marmitop stores only the invoice status, key, and number. Legal retention (5 years) is web-nf's duty, and the restaurant should know that before it deletes its web-nf account.
