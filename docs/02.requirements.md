# 02. Requirements

Each requirement has a stable ID. Tasks, tests, and code comments reference these IDs (`// covers FR-022`). Functional requirements start with `FR`. Non-functional requirements start with `NFR`.

Each FR has one testable sentence, an **Acceptance** note (how a test or a reviewer decides pass or fail), and a **Trace** (ADR, screen component, or both). Screen components are the files in `components/` today. They move to `apps/dashboard` (ADR-001). Routes come from ADR-004.

Terms:

* **Restaurant**: the tenant. Every tenant row has `restaurant_id`.
* **Admin** and **attendant**: the two roles in `restaurant_members` (FR-004).
* **Status**: the order status `aguardando`, `confirmado`, `pronto`, `saiu`, `finalizado`, or `cancelado` (ADR-028). These names stay in Portuguese.
* **Final status**: `finalizado` or `cancelado`.
* **Gateway**: a port with a real adapter and a fake (`WhatsAppGateway`, `InvoiceGateway`).
* Money is `bigint` cents (ADR-006).

## Functional requirements

### Authentication and roles (FR-001 to FR-009)

* **FR-001** — A visitor can log in at `/login` with email and password through Supabase Auth.
  * Acceptance: valid credentials open `/messages`; wrong credentials show an error and create no session.
  * Trace: ADR-005; screen `/login` (new).
* **FR-002** — A logged-in user can log out, and the session ends at once.
  * Acceptance: after logout, any dashboard route redirects to `/login`.
  * Trace: ADR-005; `nav-sidebar.tsx` (logout control, new).
* **FR-003** — The system redirects every unauthenticated request for a dashboard route to `/login`.
  * Acceptance: a request without a session to `/orders` returns a redirect to `/login`.
  * Trace: ADR-005 (middleware).
* **FR-004** — Each user belongs to a restaurant through `restaurant_members` with a role of `admin` or `attendant`.
  * Acceptance: the service layer reads the restaurant and role from `restaurant_members`, never from client input.
  * Trace: ADR-005, ADR-004.
* **FR-005** — The attendant can open messages, orders, new order, and contacts. The admin can open every screen.
  * Acceptance: an attendant request for `/menu`, `/stock`, `/reports`, `/finance`, or `/settings` gets `403` or a redirect; the admin can open all nine screens.
  * Trace: ADR-005; `nav-sidebar.tsx`.
* **FR-006** — The service layer checks the role on every write and every read of an admin-only resource.
  * Acceptance: a test calls each admin-only service as an attendant and gets a forbidden error.
  * Trace: ADR-005.
* **FR-007** — The navigation hides the items that the role cannot open.
  * Acceptance: an attendant sees four items in the sidebar; an admin sees eight.
  * Trace: ADR-005; `nav-sidebar.tsx`.
* **FR-008** — The system never trusts a restaurant id, user id, or role sent by the browser.
  * Acceptance: a Server Action called with a foreign `restaurant_id` writes nothing to that restaurant.
  * Trace: ADR-004, ADR-005.
* **FR-009** — The seed creates one demo restaurant with one admin and one attendant.
  * Acceptance: after `scripts/seed`, both users can log in and see only their own role's screens.
  * Trace: ADR-005 (consequences).

### Messages (FR-010 to FR-019)

* **FR-010** — The messages screen lists the restaurant's WhatsApp conversations, newest `last_message_at` first, each with customer name, last-message preview, time, and unread count.
  * Acceptance: three seeded conversations render in descending order with the stored preview and count.
  * Trace: ADR-002, ADR-004; `contacts-sidebar.tsx`, route `/messages`.
* **FR-011** — The user can search conversations by customer name, phone, or preview text.
  * Acceptance: typing a partial name filters the list; an empty term shows all.
  * Trace: `contacts-sidebar.tsx` ("Buscar clientes...").
* **FR-012** — An inbound message increases the conversation's `unread_count` by one. Opening the conversation resets it to zero. The navigation badge shows the total.
  * Acceptance: two inbound messages give 2; opening the thread gives 0 and the badge drops by 2.
  * Trace: `nav-sidebar.tsx` (badge), `contacts-sidebar.tsx`.
* **FR-013** — Opening a conversation shows its messages in time order with direction (`in` or `out`) and delivery status (`pending`, `sent`, `delivered`, `read`, `failed`).
  * Acceptance: seeded messages render in `created_at` order; the status of an outbound message appears.
  * Trace: `chat-panel.tsx`.
* **FR-014** — The user can send a text reply. The system stores the message as `pending`, enqueues an outbound job, and shows the message at once. FR-117 applies first.
  * Acceptance: Enter sends; Shift+Enter adds a line; an empty or blank text sends nothing; a `messages` row and a job exist.
  * Trace: ADR-002, ADR-007; `chat-panel.tsx`.
* **FR-015** — The messages screen updates without a reload when a message or a conversation changes.
  * Acceptance: an inbound webhook in one browser session shows the message in an open session within 2 seconds (NFR-021).
  * Trace: ADR-004 (Realtime); `chat-panel.tsx`.
* **FR-016** — A message can carry an `order_id`. The chat shows it as a `Pedido #ORD-001` tag. Clicking the tag highlights that order in the orders panel.
  * Acceptance: a message with `order_id` renders the tag with the order code; a click scrolls to and highlights the order card.
  * Trace: `chat-panel.tsx` (`onOrderClick`), `orders-panel.tsx` (`highlightedOrderId`).
* **FR-017** — The user can create an order from the open chat. The new-order form opens with the customer filled in, and the saved order has `source = whatsapp` and the `conversation_id`.
  * Acceptance: the saved order links to the conversation; the system adds a message to the chat that carries the new `order_id`.
  * Trace: `chat-panel.tsx` (`onCreateOrder`), `manual-order-page.tsx`.
* **FR-018** — The orders panel beside the chat lists the open conversation customer's orders grouped by status and lets the user move an order to a valid next status.
  * Acceptance: the panel shows only that customer's orders; a move uses the same service as the board (FR-021).
  * Trace: `orders-panel.tsx`.
* **FR-019** — A failed outbound message shows the status `failed` and a retry action.
  * Acceptance: after the retry limit (ADR-007), the row shows `failed`; retry enqueues a new attempt.
  * Trace: ADR-002, ADR-007; `chat-panel.tsx`.

### Orders board (FR-020 to FR-029)

* **FR-020** — The board shows one column per status: `aguardando`, `confirmado`, `pronto`, `saiu`, `finalizado`, and `cancelado` (ADR-028). Each card shows the code, customer, items, total, and time.
  * Acceptance: seeded orders appear in the column of their status.
  * Trace: `orders-page.tsx` (`COLUMNS`, `KanbanColumn`, `OrderCard`), route `/orders`.
* **FR-021** — The user can drag a card to another column. The server accepts the move only if the transition is valid (FR-022). An invalid move returns the card to its column and shows an error.
  * Acceptance: dragging `finalizado` back to `pronto` is rejected and the status stays; dragging `aguardando` to `pronto` succeeds and writes one history row.
  * Trace: ADR-017; `orders-page.tsx` (`handleDragEnd`, today it accepts any move).
* **FR-022** — The transition rules are (ADR-017, ADR-028):
  * a forward move may skip columns along `aguardando → confirmado → pronto → saiu → finalizado`, so `aguardando → pronto` is one move and writes one history row;
  * a pickup order never enters `saiu` (`aguardando → confirmado → pronto → finalizado`);
  * a backward move goes one step only, except from a final status;
  * any non-final status can move to `cancelado`;
  * `finalizado` and `cancelado` are final, so no move leaves them;
  * a move to the current status is a no-op and writes no history.
  * Acceptance: a unit test covers every pair of statuses for delivery and for pickup, and the database trigger agrees with it.
  * Trace: `packages/core` status machine; ADR-017 (replaces the brief's one-step rule); 05.data-model.md "Order status transitions".
* **FR-023** — Every status change writes one `order_status_history` row with `from_status`, `to_status`, `changed_by`, and `changed_at`, in the same transaction as the change. Creating an order writes the first row.
  * Acceptance: after three moves the order has four history rows in order; a failed move writes none.
  * Trace: data model `order_status_history`.
* **FR-024** — The user can search the board by order code, customer name, or item name.
  * Acceptance: "ORD-002", a partial name, and an item name each filter the cards.
  * Trace: `orders-page.tsx` ("Buscar por pedido, cliente ou item...").
* **FR-025** — The board shows four daily KPIs for the restaurant's current day (timezone from settings): revenue and count of `finalizado` orders ("Faturamento finalizado"); in progress (`aguardando`, `confirmado`); ready (`pronto`); out for delivery (`saiu`).
  * Acceptance: with a fixed clock and seeded orders, each KPI equals the expected value; an order finalized yesterday does not count.
  * Trace: `orders-page.tsx` (`KpiCard`).
* **FR-026** — The user can cancel an order that is not in a final status. The cancel records the history row and keeps the order.
  * Acceptance: cancel from `confirmado` gives `cancelado` and a history row; cancel from `finalizado` is rejected.
  * Trace: FR-022.
* **FR-027** — The board updates without a reload when an order is created or changes.
  * Acceptance: an order created in one session appears in another session within 2 seconds (NFR-021).
  * Trace: ADR-004 (Realtime on `orders`).
* **FR-028** — Moving an order to `finalizado` sets `delivered_at`. The column keeps its name; it holds the time the order was finalized (ADR-028).
  * Acceptance: `delivered_at` is set once, at the move, and feeds FR-025 and FR-070.
  * Trace: data model `orders.delivered_at`.
* **FR-029** — When the restaurant setting "Aceitar pedidos automaticamente" is on, a new order starts as `confirmado`. Otherwise it starts as `aguardando`. An order from the AI assistant always starts as `aguardando` (FR-211, ADR-027).
  * Acceptance: both settings give the expected first history row.
  * Trace: FR-081; `settings-page.tsx`.

### New order (FR-030 to FR-039)

* **FR-030** — The user can pick an existing customer or create one inline (name and phone).
  * Acceptance: a new phone creates a customer; an existing phone reuses it (FR-047).
  * Trace: `manual-order-page.tsx` (customer select), route `/new-order`.
* **FR-031** — The user can add menu items to the order, choose a size for items that have sizes, and set the quantity.
  * Acceptance: the cart keeps one line per item and size; the same item with another size is a separate line. (Today the prototype always uses the first size.)
  * Trace: `manual-order-page.tsx`, ADR-006.
* **FR-032** — The product list shows only available items offered on the current weekday, and the search narrows it.
  * Acceptance: an item with `available = false` or without today's weekday is not listed; the service rejects it too.
  * Trace: `manual-order-page.tsx` ("Marmita"/"Bebida" list), FR-054, FR-056.
* **FR-033** — The user chooses `delivery` or `pickup`. Pickup is available only when the setting allows it.
  * Acceptance: with pickup off, the form offers only delivery and the service rejects `pickup`.
  * Trace: FR-081.
* **FR-034** — Orders and customers store a structured address: `cep`, `logradouro`, `numero`, `complemento`, `bairro`, `cidade`, `uf`, `codigo_municipio` (ADR-016). A delivery order requires `logradouro` and `bairro`. The form copies the address from the customer, and `cidade`, `uf`, and `codigo_municipio` default to the restaurant's values. The UI shows the address as one line built from the parts. v1 has no CEP lookup.
  * Acceptance: a delivery order without `logradouro` or `bairro` is rejected with a field error; a new address gets the restaurant's city, state, and IBGE code.
  * Trace: ADR-016; data model `orders`, `customers`, `restaurants`.
* **FR-035** — The user chooses a payment method: `pix`, `dinheiro`, `cartao_credito`, or `cartao_debito`. For `dinheiro` the user can enter a change amount. The manual form still requires it; only assistant orders start with none (FR-188).
  * Acceptance: `change_for_cents` must be at least the total; other methods ignore it.
  * Trace: data model `orders.payment_method`, `change_for_cents`.
* **FR-036** — The user can add a note to the order and a note to each item.
  * Acceptance: both notes persist and show on the card and in the detail.
  * Trace: `order_items.notes`, `orders.notes`.
* **FR-037** — The server computes the total: `sum(unit_price × qty) + delivery_fee`. The delivery fee applies to delivery orders only. The client sends item ids, size ids, and quantities, never prices.
  * Acceptance: unit tests cover pickup, delivery, several sizes, and a tampered client price (ignored). The form shows a preview that the server confirms on save.
  * Trace: ADR-006; `packages/core` `computeOrderTotal`.
* **FR-038** — The server snapshots name, size name, and unit price into `order_items` and assigns the code `ORD-NNN` from a per-restaurant sequence.
  * Acceptance: a later price change leaves the order unchanged; two orders never share a code.
  * Trace: ADR-006.
* **FR-039** — Saving an order creates the first history row, the `order_received` automatic message when the order has a WhatsApp conversation (FR-112), a `usage_events` row, and the `order.created` webhook event (FR-146). All happen in the same transaction or by jobs queued in it.
  * Acceptance: one test checks all four effects after one save.
  * Trace: ADR-007, ADR-008, ADR-009.

### Contacts (FR-040 to FR-049)

* **FR-040** — The contacts screen lists customers with name, phone, `bairro`, "Cliente desde", number of orders, and total spent.
  * Acceptance: seeded customers show the stored values and computed totals.
  * Trace: `contacts-page.tsx`, route `/contacts`.
* **FR-041** — The user can search contacts by name, phone, or `bairro`.
  * Acceptance: each of the three terms finds the customer; no match shows the empty state.
  * Trace: `contacts-page.tsx` ("Buscar por nome, telefone ou bairro...").
* **FR-042** — Clicking a contact opens a detail sheet with phone, email, the one-line address, and "Cliente desde".
  * Acceptance: the sheet shows the stored fields.
  * Trace: `contacts-page.tsx` (`ContactSheet`).
* **FR-043** — The sheet lists the customer's orders, newest first, with code, status, and total.
  * Acceptance: only that customer's orders appear.
  * Trace: `ContactSheet`.
* **FR-044** — The sheet and the list show total orders and total spent. Total orders excludes `cancelado`. Total spent counts `finalizado` orders only (ADR-015, ADR-028).
  * Acceptance: a customer with two `finalizado` orders, one `confirmado` order, and one cancelled order shows 3 orders and the sum of the two `finalizado` ones.
  * Trace: `ContactSheet` stats; ADR-015.
* **FR-045** — The user can create a customer with name and phone, and optionally email, CPF or CNPJ, the structured address (FR-034), and notes.
  * Acceptance: a missing name or phone gives a field error; `cep` with other than 8 digits gives a field error.

* **FR-046** — The user can edit every field of a customer.
  * Acceptance: an edit persists and shows in the list and in open chats.
  * Trace: `ContactSheet` (edit action, new).
* **FR-047** — The system stores the phone in E.164 format and rejects a second customer with the same phone in the same restaurant.
  * Acceptance: "(11) 99999-0000" is stored as `+5511999990000`; a duplicate returns a conflict error.
  * Trace: data model `customers.phone`.
* **FR-048** — An inbound message from an unknown phone creates a customer and a conversation.
  * Acceptance: the first inbound message adds one customer; the second adds none.
  * Trace: FR-105.
* **FR-049** — Customers of other restaurants never appear.
  * Acceptance: covered by NFR-001.
  * Trace: NFR-001.

### Reports (FR-070 to FR-079)

Definitions for this section: a **counted order** is an order in status `finalizado` (ADR-028). The report date is `delivered_at` in the restaurant timezone.

* **FR-070** — The reports screen shows revenue for the period: the sum of `total_cents` of counted orders.
  * Acceptance: an aggregation test with a fixed dataset gives the exact sum; cancelled and open orders add nothing.
  * Trace: ADR-015; `reports-page.tsx` ("Faturamento total"), route `/reports`.
* **FR-071** — The screen shows the number of counted orders.
  * Acceptance: matches the dataset.
  * Trace: `reports-page.tsx` ("Total de pedidos").
* **FR-072** — The screen shows the average ticket: revenue divided by the count, rounded to the cent, and zero when the count is zero.
  * Acceptance: no division error on an empty period.
  * Trace: `reports-page.tsx` ("Ticket médio").
* **FR-073** — The screen shows active customers: customers with at least one counted order in the period.
  * Acceptance: a customer with only cancelled orders is not active. (The prototype counts all contacts.)
  * Trace: ADR-015; `reports-page.tsx` ("Clientes ativos").
* **FR-074** — The screen shows revenue per month for the last six months, including the current month, with zero for empty months.
  * Acceptance: six points in order; months with no orders show 0.
  * Trace: `reports-page.tsx` (monthly chart, `RevenueTooltip`).
* **FR-075** — The screen shows orders per day for the last 14 days, including today, with zero for empty days.
  * Acceptance: fourteen points in order.
  * Trace: `reports-page.tsx` (daily chart, `DailyTooltip`).
* **FR-076** — The screen shows the top-selling items by quantity sold, from `order_items` of counted orders, with ties broken by name.
  * Acceptance: the list is stable and limited to eight rows.
  * Trace: `reports-page.tsx` (top items bar chart).
* **FR-077** — The screen shows the revenue change of the current month against the previous month as a percent.
  * Acceptance: previous month zero shows "—", not infinity.
  * Trace: `reports-page.tsx` (`revenueGrowth`).
* **FR-078** — All aggregations use pure functions in `packages/core`, fed by rows from `packages/db`.
  * Acceptance: the functions run in tests with no database.
  * Trace: NFR-050.
* **FR-079** — Only the admin can open the reports screen.
  * Acceptance: see FR-005.
  * Trace: ADR-005.

### Settings (FR-080 to FR-099)

All settings need the admin role (FR-098).

* **FR-080** — The admin can edit the restaurant profile: name, phone, email, address, `cidade`, `uf`, and `codigo_municipio`. The last three are the defaults for new customer and order addresses (ADR-016).
  * Acceptance: saved values show after reload; a new customer address starts with these three values.
  * Trace: `settings-page.tsx` (`RestaurantSettings`), route `/settings`.
* **FR-081** — The admin can switch on or off: accept orders automatically, allow pickup, and show the delivery estimate.
  * Acceptance: each switch changes the behavior in FR-029, FR-033, and the customer messages.
  * Trace: `RestaurantSettings` ("Preferências de pedidos"), `restaurant_settings`.
* **FR-082** — The admin can set the delivery fee (cents) and the delivery estimate (minutes).
  * Acceptance: the fee feeds FR-037.
  * Trace: `restaurant_settings.delivery_fee_cents`, `delivery_estimate_minutes`.
* **FR-083** — The admin can set business hours per weekday: enabled, opening time, closing time.
  * Acceptance: seven rows persist; closing earlier than opening means the window ends after midnight.
  * Trace: `settings-page.tsx` (`HoursSettings`), `business_hours`; FR-113.
* **FR-084** — The admin can enable and edit the text of the seven automatic messages: `welcome`, `closed`, `order_received`, and the four order status kinds of FR-200 (ADR-028). For `order_received` and each status kind the admin can also pick an approved WhatsApp template from `backend-uatis` (ADR-014, ADR-026, FR-117).
  * Acceptance: seven rows persist with `enabled` and `body`; `welcome` and `closed` refuse a template.
  * Trace: `AutomationSettings`, `automatic_messages`; FR-110 to FR-112.
* **FR-085** — The admin can save the `backend-uatis` connection: base URL, API key, `phone_number_id`, and optionally a webhook secret. The system encrypts both secrets. The webhook secret is optional because FR-170 registers the webhook and stores its secret; a secret typed by hand is for an API key that cannot manage webhooks (ADR-021, ADR-023).
  * Acceptance: a saved connection has `status = connected` only after FR-086 succeeds; the key is never returned.
  * Trace: ADR-002, ADR-012; `IntegrationSettings` (rebuilt).
* **FR-086** — The admin can test the WhatsApp connection. The result and `status` show on the screen.
  * Acceptance: a call to the gateway health or list endpoint sets `connected` or `error` with a message.
  * Trace: ADR-002; `integrations_whatsapp.status`.
* **FR-087** — The admin can set the outbound webhook URL and choose the events to send.
  * Acceptance: only `https` URLs pass in production; events come from the list in FR-146.
  * Trace: ADR-009; `IntegrationSettings` ("URL do webhook de pedidos").
* **FR-088** — The system generates the webhook signing secret, shows it once, and lets the admin rotate it.
  * Acceptance: a second read returns only "configured" and the last four characters.
  * Trace: ADR-009, ADR-012.
* **FR-089** — The admin can create and revoke API keys. The full key shows once. The list shows name, prefix, environment (`live` or `test`), last use, and revoked state.
  * Acceptance: the database holds the SHA-256 hash and the prefix only.
  * Trace: ADR-009; `IntegrationSettings` ("Chave de API").
* **FR-090** — The admin can save the fiscal configuration: `web-nf` base URL, API key, webhook secret, environment, NFC-e series, NFe series, and defaults for NCM, CFOP, CSOSN, PIS CST, and COFINS CST.
  * Acceptance: all defaults are required before FR-120 is allowed.
  * Trace: ADR-003, ADR-012; `integrations_fiscal`.
* **FR-091** — The admin can test the fiscal connection.
  * Acceptance: the result shows `connected` or the error from `web-nf`.
  * Trace: ADR-003.
* **FR-092** — The settings screen has a plan tab that shows the plan name and the usage for the current month: orders, messages sent, and invoices issued.
  * Acceptance: counts equal the `usage_events` rows of the month.
  * Trace: ADR-008; `settings-page.tsx` (new tab).
* **FR-093** — The plan tab shows an invoice history list. In v1 it is empty and says so.

### backend-uatis webhook and event feed (FR-170 to FR-179)

FR-100 to FR-119 are full, so these requirements continue the WhatsApp channel here (ADR-021, amended by ADR-023). Terms: a **push** webhook makes `backend-uatis` POST each event to Marmitop; a **pull** webhook has no URL, and Marmitop reads the **event feed** `GET /v1/webhooks/{id}/events`. Both deliver the same event envelope.

* **FR-170** — "Ativar webhook" in Settings → WhatsApp reads the API key's organization (`GET /v1/organizations/current`) and registers a `backend-uatis` webhook with `events = [message.created, message.updated]`. When `MT_PUBLIC_URL` passes FR-172 it registers `mode: push` with `url = MT_PUBLIC_URL + /v1/webhooks/uatis/{restaurant_id}` and seals the returned secret as the restaurant's `uatis_webhook_secret`, replacing any stored one. Otherwise it registers `mode: pull` with no URL, and the stored secret stays as it is. The service stores `uatis_webhook_id`, `uatis_webhook_mode`, and `uatis_organization_id`, clears `uatis_feed_cursor`, and writes an `audit_logs` row `integration.whatsapp.webhook_enable` with the webhook id, the mode, and the secret's last four characters when there is one.
  * Acceptance: with a public URL, the fake server has one push webhook with that URL and both events, and the stored secret opens to the returned value; with `http://localhost:3101`, it has one pull webhook and no secret changes. A key below `admin` gets `403` from `backend-uatis`, and Settings shows "A chave da API do Uatis precisa ser de administrador.".
  * Trace: ADR-021, ADR-023, ADR-012; `enableUatisWebhook`.
* **FR-171** — Registering again first deletes the webhook in `uatis_webhook_id`, then creates the new one. A `404` from the delete counts as done. When the create fails, `uatis_webhook_id` and `uatis_webhook_mode` are cleared, so the restaurant falls back to the timestamp poll, and the error shows in pt-BR.
  * Acceptance: two enables leave one webhook at `backend-uatis`; a create refused with `403` leaves `uatis_webhook_id` null.
  * Trace: ADR-021, ADR-023.
* **FR-172** — `MT_PUBLIC_URL` qualifies for push when it is an absolute `https` URL on port 443, with no user name, password, query, or fragment, on a host that is not `localhost`, a private name, or a private, loopback, or link-local address. `MT_ALLOW_PRIVATE_HOSTS` does not relax this rule. A URL that fails selects pull; it never disables the button. No tunnel is needed or recommended (ADR-023).
  * Acceptance: `http://localhost:3101`, `https://10.0.0.5`, `https://x.example.com:8443`, and an empty value select pull; `https://api.example.com` selects push.
  * Trace: ADR-021, ADR-023; 07.security.md "SSRF guard".
* **FR-173** — "Desativar webhook" calls `DELETE /v1/webhooks/{id}` and clears `uatis_webhook_id`, `uatis_webhook_mode`, `uatis_organization_id`, and `uatis_feed_cursor`. The webhook secret stays, so a webhook registered by hand keeps working. A `404` counts as done. Any other gateway failure leaves the row as it was and shows the error. The restaurant falls back to the 30-second timestamp poll.
  * Acceptance: after disabling, Settings shows "Não registrado"; an audit row `integration.whatsapp.webhook_disable`.
  * Trace: ADR-021, ADR-023.
* **FR-174** — Event feed. The worker job `mt_sync` op `uatis_feed_pull` reads the feed of a connected restaurant with a registered webhook: every `MT_UATIS_PULL_SECONDS` seconds (default 3) in pull mode, every 5 minutes in push mode. The worker enqueues these jobs with `mt.enqueue_uatis_feed_pulls(pull_seconds)` on a timer of the same length. It reads from `uatis_feed_cursor` (`after`), at most 20 pages of 100, and runs each event through the same handler as the webhook route (FR-176). A page shorter than the limit ends the run: `next_cursor` echoes `after` when nothing is new, so it never means "more". Each event commits in its own transaction together with its cursor, so the cursor advances only after the event commits. `410 cursor_expired`, and `400` for a foreign cursor, set the cursor to null and log a warning. On `404` the job asks `GET /v1/webhooks/{id}`: when the webhook exists, `backend-uatis` has no feed, and the job runs the timestamp poll from FR-107; when it is gone, the job clears the webhook columns and runs the timestamp poll. `403` (a key below `admin`) sets the integration to `error` with "A chave da API do Uatis precisa ser de administrador.". The 30-second timestamp poll (`mt.enqueue_whatsapp_sync`) skips push webhooks and runs every 10 minutes for pull webhooks, as a safety net for a `backend-uatis` transaction that commits behind the cursor (ADR-023).
  * Acceptance: a feed of three events applies three and stores the third cursor; a failure on the second leaves the cursor at the first; a `410` or a `400` resets the cursor; a `404` with the webhook present calls `GET /v1/messages`; a `404` with the webhook gone clears it; a restaurant in pull mode last pulled 1 second ago is not enqueued with `pull_seconds = 3`, and one pulled 4 seconds ago is; a pull restaurant last polled 11 minutes ago gets a timestamp poll, and a push restaurant never does.
  * Trace: ADR-023; migration 0019.
* **FR-175** — Push requests also check `organization_id` in the body against `uatis_organization_id`. A mismatch or a missing value gets the same `401 signature_invalid` as a bad signature. When `uatis_organization_id` is null (a secret typed by hand), the check is skipped. Feed events whose `organization_id` differs are skipped with a warning.
  * Acceptance: a correctly signed body with another `organization_id` gets `401` and writes nothing.
  * Trace: ADR-021, ADR-023; FR-118.
* **FR-176** — One handler for both paths, `applyUatisEvent`. It records the event id (`X-Uatis-Delivery`, the body `id`, the feed event `id`) in `uatis_event_receipts` and skips an id it has seen, then applies a message event as in FR-104 to FR-106. The receipt and the message rows commit together. Every accepted push request also sets `last_webhook_at`.
  * Acceptance: the same event pushed and then pulled is applied once; a pushed replay answers `200` and changes nothing; `last_webhook_at` equals the server time of the push.
  * Trace: ADR-023; 07.security.md "Inbound webhook verification".
* **FR-177** — `message.updated` moves an outbound status forward as in FR-106, including `delivered` and `read`. A move to `failed` also stores `error_code` (`whatsapp_<code>` from `status.errors[0].code`, or `whatsapp_failed`) and `error_message` (its `title` or `message`, at most 200 characters). States Marmitop does not know (`accepted`, `held_for_quality_assessment`) change nothing.
  * Acceptance: `sent` then `delivered` then `read` ends at `read`; `failed` with error 131047 gives `whatsapp_131047`.
  * Trace: ADR-021; FR-106.
* **FR-178** — Settings → WhatsApp shows the webhook state ("Ativo" or "Não registrado"), the mode ("Push" or "Pull") with a pt-BR line that explains it, the mode the next "Ativar webhook" will pick and why, the time of the last push received and of the last feed read, and the last five `backend-uatis` delivery attempts (`GET /v1/webhooks/{id}/deliveries?limit=5`). A gateway failure while reading the attempts shows a short pt-BR note instead of the list, and the rest of the page still renders.
  * Acceptance: with the gateway failing, the page renders and shows the note.
  * Trace: ADR-021, ADR-023; `getUatisWebhookStatus`, `settings-page.tsx` (`UatisWebhookPanel`).
* **FR-179** — Only the admin calls `enableUatisWebhook`, `disableUatisWebhook`, and `getUatisWebhookStatus`. In production (`MT_ENV=production`) the `backend-uatis` base URL must be `https`.
  * Acceptance: an attendant gets `forbidden` from each; `http://uatis.example.com` is refused in production.
  * Trace: ADR-005, ADR-023 security rule 2; FR-098.

### AI order assistant (FR-180 to FR-199)

The assistant ("Atendente IA") talks with customers on WhatsApp, takes the order, asks "Retirada ou Entrega?", asks for the address for Entrega, and creates the order (ADR-025). 12.ai-order-assistant.md holds the design, the tool contracts, and the terms **turn**, **AI reply**, **burst**, **cart**, **summary**, and **pause**.

* **FR-180** — Configurações → Atendente IA lets the admin turn the assistant on or off and set `persona_name`, `extra_instructions`, `auto_resume_minutes`, "Continuar e pagar pelo uso" (`allow_overage`), and `monthly_hard_cap`. It is off for a new restaurant. The card says that the AI reads customer messages and that Anthropic processes them.
  * Acceptance: a new restaurant has `ai_settings.enabled = false`; an attendant gets `forbidden` on save.
  * Trace: ADR-025; `ai_settings`; `settings-page.tsx` (`AiAssistantCard`, new).
* **FR-181** — A new inbound message enqueues one `mt_ai_turns` job with an 8-second delay, in the ingest transaction, only when the assistant is on, the conversation is not paused (or its `attendant` or `manual` pause is older than `auto_resume_minutes`, FR-189), the restaurant is open, no `closed` message was sent for it, and the quota allows a reply (FR-196). A job that waits on another turn's claim (`locked`) is re-enqueued every 5 seconds with the same `enqueuedAt`.
  * Acceptance: each of the five conditions, when false, gives no job; a duplicate inbound gives no job.
  * Trace: ADR-025; `enqueueAiTurn`, `ingestInboundMessage`.
* **FR-182** — A burst gives one turn. A job whose trigger is not the latest inbound message ends as `superseded` with no model call. Two jobs never run the same conversation at the same time.
  * Acceptance: three inbound messages in 2 seconds give three jobs, one `replied` run, and two `superseded` runs.
  * Trace: 12.ai-order-assistant.md "Guards in the worker".
* **FR-183** — A job ends with no model call as `paused`, `answered`, `stale` (older than 120 seconds), or `blocked` (quota) under the rules in 12.ai-order-assistant.md. `stale` and `blocked` pause the conversation.
  * Acceptance: one integration test per status.
  * Trace: 12.ai-order-assistant.md "Guards in the worker".
* **FR-184** — The assistant asks for the items, then "Retirada ou Entrega?", then, for Entrega, `logradouro`, `numero`, and `bairro`, with `complemento` when the customer gives one. It never asks for the payment method. `cidade`, `uf`, and `codigo_municipio` take the restaurant's values (FR-034). Retirada is offered only when `allow_pickup` is on.
  * Acceptance: `update_cart` reports `missing` from items, fulfillment, `logradouro`, and `bairro` only; `pickup` fails with `pickup_disabled` when the setting is off; the eval suite has no case where the assistant asks about payment.
  * Trace: ADR-025 Decision 2; tool `update_cart`.
* **FR-185** — The assistant names and prices only items on today's menu (FR-032 rules). The cart stores item ids, sizes, and quantities, never prices. Every `update_cart` call returns the subtotal, delivery fee, and total from `computeOrderTotal`.
  * Acceptance: an archived, unavailable, or off-weekday item is rejected with `item_unavailable`; a price change between two calls changes the returned total.
  * Trace: FR-032, ADR-006; tools `search_menu`, `update_cart`.
* **FR-186** — `place_order` creates an order only after `send_order_summary` sent a server-rendered summary of the current cart version and the customer sent a message after it, within 30 minutes, while the restaurant is open. Otherwise it fails with `not_confirmed` or `closed`.
  * Acceptance: a call with no summary, with a cart changed after the summary, with no inbound message after the summary, or after closing time writes no order.
  * Trace: ADR-025 Decision 2 "Confirmation".
* **FR-187** — `place_order` creates the order through `createOrderInTx` with `source = 'whatsapp'`, `payment_method = null`, the conversation id, and `ai_run_id`. The FR-029 initial status, the first history row, `order_received`, usage, and `order.created` follow as for any order (FR-039). A second call returns the same order. Empty saved customer name and address fields take the order's values; saved values stay.
  * Acceptance: the order row has `source = 'whatsapp'`, null `payment_method`, and `ai_run_id`; two calls give one order; a customer with a saved address keeps it.
  * Trace: FR-029, FR-034, FR-039; `createOrderInTx`.
* **FR-188** — `orders.payment_method` may be null ("A definir"). The board card, the order detail, finance, and reports show "A definir". Attendant and admin set it in the order detail (`setOrderPaymentMethod`). A set method changes only while the order has no active invoice (`invoice_active` conflict otherwise), and each change is audited. The public API and outbound webhooks send `payment_method: null`. "Emitir NF" asks for it in the FR-125 gap form.
  * Acceptance: an order with null payment shows "A definir"; setting `pix` saves it; the invoice gap form lists the payment method.
  * Trace: ADR-025 Decision 2 "Payment method"; FR-035, FR-125.
* **FR-189** — While the assistant is on, an attendant reply from the dashboard pauses the assistant for that conversation with reason `attendant`. While it is off, an attendant reply changes no AI state. The conversation header shows the state and a Pausar or Retomar button. A conversation paused for `attendant` or `manual` resumes on the next inbound message after `auto_resume_minutes` (0 means never).
  * Acceptance: after an attendant reply, the next inbound message gives no job; after `auto_resume_minutes`, it does; with the assistant off, an attendant reply leaves `ai_mode = 'auto'`.
  * Trace: ADR-025; `chat-panel.tsx`.
* **FR-190** — `handoff_to_human` pauses the conversation with its reason and note. The assistant hands off when the customer asks for a person, complains, asks about an existing order, wants to change or cancel one, or sends media. The list filter "Precisa de atendente" shows conversations paused for any reason except `attendant` and `manual`.
  * Acceptance: a handoff shows the conversation under the filter with the note.
  * Trace: tool `handoff_to_human`.
* **FR-191** — A turn makes at most 6 model calls. A `refusal`, a `max_tokens` stop, or the call cap sends no reply and pauses the conversation with reason `model`.
  * Acceptance: the scripted fake returns `refusal`; no outbound row; the conversation is paused.
  * Trace: 12.ai-order-assistant.md "Tool loop".
* **FR-192** — Assistant replies go out through the FR-016 path, at most 1000 characters, with `messages.ai_run_id` set. The inbox tags them "IA".
  * Acceptance: the outbound row has `ai_run_id` and an `mt_outbound_messages` job.
  * Trace: FR-016.
* **FR-193** — The board card and the order detail tag an order with `ai_run_id` as "IA".
  * Acceptance: an order from the assistant shows the tag; a counter order does not.
  * Trace: `orders-page.tsx`.
* **FR-194** — Each plan has `included_ai_replies_month` and `ai_overage_price_cents` (per 100 replies). Seed values: Free 300, Pro 3,000, and 500 cents for both.
  * Acceptance: after migration 0020, both plans carry the seed values.
  * Trace: ADR-025 Decision 4; `plans`.
* **FR-195** — No tool input names a restaurant, customer, or conversation. Every tool runs in `withRestaurantContext` for the job's restaurant.
  * Acceptance: an RLS integration test runs every tool for restaurant A and sees no row of restaurant B.
  * Trace: NFR-001; ADR-025.
* **FR-196** — Each customer message whose turn calls the model writes one `usage_events` row `ai.reply` with `ref_id` = the trigger message id, so a retry of the same message is not billed again. Each attempt writes one `ai_runs` row with `billed_as`. The quota state is `included` below the plan amount; `overage` above it when `allow_overage` is on and the count is below `monthly_hard_cap`; blocked otherwise. A blocked state gives no job and pauses the conversation with reason `quota` or `cap`.
  * Acceptance: at the included amount with overage off, the next inbound message gives no job and the conversation shows `quota`; with overage on, the turn runs with `billed_as = 'overage'`; at the hard cap, no job in either case.

* **FR-198** — The model sits behind the `AssistantModel` port with `AnthropicAssistantModel` and `ScriptedAssistantModel`. `MT_AI_MODEL` (default `claude-haiku-5-5`) and `MT_AI_EFFORT` (default `low`) configure it. With an empty `ANTHROPIC_API_KEY` (fake mode) each AI turn records usage, fails, and pauses with `model`.
  * Acceptance: the worker starts with the scripted adapter when `ANTHROPIC_API_KEY` is empty and logs that the assistant is in fake mode; a log capture during a scripted turn has no customer text and no key prefix.

### Order status messages (FR-200 to FR-209)
