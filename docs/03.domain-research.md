# 03. Domain research — NFe, NFC-e, NFSe, and WhatsApp

This document explains the fiscal and messaging domains behind Marmitop. It drives three decisions: why orders use NFC-e (ADR-003), how Marmitop maps an order to a `web-nf` request (08), and how the WhatsApp channel works (ADR-002).

Marmitop does not talk to SEFAZ. `web-nf` does. Marmitop sends a JSON request and reads the result. The sections on SEFAZ, XML, and certificates explain what happens behind that call, so that the team can read an error and know where it came from.

The base research comes from `web-nf/docs/03.domain-research.md` and its appendix (same owner). This version was re-checked against primary sources on 2026-10-13. Section "Verification notes" lists what changed.

Labels: **VERIFIED-PRIMARY** means read on the official page on 2026-10-13. **VERIFIED-SECONDARY** means two or more independent secondary sources agree (taken from the `web-nf` research). **UNVERIFIED** means one source only, or memory; confirm before relying on it.

## 1. NFe (modelo 55) — goods

* NFe is the electronic invoice for the sale and transport of goods. The issuer builds an XML (layout 4.00), signs it, and sends it to the SEFAZ of its state. SEFAZ checks it and returns an authorization protocol (`protocolo`). The signed XML plus the protocol form the legal document. **VERIFIED-PRIMARY** that the MOC 7.0 defines the integration between SEFAZ systems and issuer systems for NF-e and NFC-e.
* The portal shows the current schema package: "Pacote de Liberação 010f", with NT 2025.002 v1.50 and NT 2026.007 v1.00, published 2026-08-31. **VERIFIED-PRIMARY**.
* Web services (SOAP over HTTPS, version 4.00): `NfeAutorizacao`, `NfeRetAutorizacao`, `NfeConsultaProtocolo`, `NfeStatusServico`, `NfeInutilizacao`, `RecepcaoEvento`, `NfeConsultaCadastro`. **VERIFIED-PRIMARY** (service list per UF on the "Relação de Serviços Web" page).
* Each UF uses its own SEFAZ or a shared virtual one. On 2026-10-13 the portal lists: SVAN for MA; SVRS (most services) for AC, AL, AP, CE, DF, ES, PA, PB, PI, RJ, RN, RO, RR, SC, SE, TO. Own authorizers: AM, BA, GO, MG, MS, MT, PE, PR, RS, SP. **VERIFIED-PRIMARY**.
* Contingency: SVC-AN and SVC-RS are shared fallback authorizers; the portal lists which UF uses which. **VERIFIED-PRIMARY**. EPEC is a last-resort event (NT 2014.001 v1.41, updated 2026-08-04). **VERIFIED-PRIMARY**.
* Access key (`chave de acesso`), 44 digits: UF(2) + AAMM(4) + CNPJ(14) + modelo(2) + série(3) + número(9) + tpEmis(1) + código(8) + DV(1). **VERIFIED-SECONDARY**.
* Since NT 2025.001 (v1.00 published 2025-03-25), an NF-e lote with a single NF-e gets a synchronous answer. **VERIFIED-PRIMARY**.
* Alphanumeric CNPJ: NT 2026.004 v1.01 (2026-06-08) updates the schema. Marmitop validates CNPJ as 14 digits with check digits; `web-nf` does the same. Revisit when alphanumeric CNPJs reach customers. **VERIFIED-PRIMARY** for the NT; the impact on Marmitop is our own reading.
* Tax reform (RTC): NT 2025.002 (now v1.52, 2026-10-01) adds IBS/CBS fields. **VERIFIED-PRIMARY**. `web-nf` treats them as additive. Marmitop v1 sends no RTC fields.

## 2. NFC-e (modelo 65) — consumer sale

* NFC-e replaces the paper sales coupon for retail sales to a final consumer. It uses the same XSD and XML layout 4.00 as NFe, with its own per-UF web service endpoints. **VERIFIED-SECONDARY**; the MOC covers both documents. **VERIFIED-PRIMARY**.
* Related official manuals: DANFE-NFC-e and QR Code technical standard v6.0 (March 2025), offline contingency manual v2.0, and the NFC-e issuer good-practices manual BP 2018.001. **VERIFIED-PRIMARY** (the `web-nf` research cited v5.0; v6.0 is current).
* Emission is synchronous in practice: one NFC-e per request, answered with the protocol. NT 2023.002 (v1.01, 2025-11-18) "elimina a denegação e o lote na NFC-e" and allows NFC-e from rural producers. **VERIFIED-PRIMARY** for the NT title. Marmitop reads the result from `web-nf`, so it sees only the final status.
* Rules on top of layout 4.00 that cause rejections (**VERIFIED-SECONDARY**):
  * The buyer (`dest`) is optional. Identification is mandatory from R$ 10.000,00, on buyer request, and for home delivery (with address). Some states set lower limits.
  * `indFinal` must be 1 (Rej 716). The presence indicator `indPres` must be 1 (presencial) or 4 (entrega a domicílio) (Rej 717).
  * The buyer is never an ICMS contribuinte (Rej 789, 718).
  * No freight values (Rej 753). Transporter data only for home delivery (Rej 754).
  * Payments must cover the total; change is declared in `vTroco` (Rej 866, 869).
  * CFOP must come from the retail set: 5101, 5102, 5103, 5104, 5115, 5401, 5403, 5405, 5656, 5933.
* **CSC and QR Code.** The CSC (Código de Segurança do Contribuinte) is a secret of 16 to 36 characters, issued per CNPJ and per environment, with an id (`idCSC`, up to 6 digits). The issuer uses it to compute a SHA-1 hash that goes into the QR Code of QR Code v2. The CSC is never written in the XML. The consumer scans the QR Code on the receipt to open the SEFAZ query page. **VERIFIED-SECONDARY**; the CSC administration web service has an official manual, "Manual Técnico de Utilização do Web Service de Administração do CSC v1.00", listed on the NT page. **VERIFIED-PRIMARY**.
* **QR Code v3.** NT 2025.001 (v1.00 to v1.03, 2025-03 to 2025-09) defines the v3 layout, which needs no CSC. `web-nf` emits v2 and keeps v3 behind configuration (web-nf ADR-015). Marmitop does not care: it only needs the CSC to exist in `web-nf` (`GET /v1/csc`). **VERIFIED-PRIMARY** for the NT; the v3 details are **VERIFIED-SECONDARY**.
* **DANFE NFC-e.** The receipt is thin (58 or 80 mm paper), shows the access key, the QR Code, and "CONSUMIDOR NÃO IDENTIFICADO" when there is no buyer. NT 2026.002 (v1.11) and NT 2026.003 add the "DANFE Simplificado Tipo 2". **VERIFIED-PRIMARY** for the NT titles.
* **Cancellation.** Cancellation of an NFC-e is allowed only in a short window, commonly 30 minutes (varies by UF). **VERIFIED-SECONDARY**. After that, the legal path is a return NFe (not in v1). The UI must warn the attendant.
* No "carta de correção" for NFC-e. **VERIFIED-SECONDARY**.

### Why NFC-e for restaurant meals

A restaurant sells prepared food to people who eat it or take it home. That is a sale of goods (ICMS) to a final consumer, usually without an identified buyer. NFC-e fits that case. NFe adds buyer data, transport data, and IE rules that a meal sale does not need. NFSe does not fit: prepared meals are goods, not services, so ISS does not apply (ADR-003). The delivery fee is the one grey area; see 08, section "Delivery fee".

In most states a restaurant has to issue NFC-e (or SAT/MFe in SP and CE) by tax rule. The exact duty depends on the UF and the tax regime. The restaurant owner and the accountant confirm it. Marmitop only makes issuing easy.

### The presence indicator (`indPres`)

`web-nf` takes `operacao.presenca` as `presencial` (indPres 1) or `entrega_domicilio` (indPres 4) for NFC-e. Marmitop uses `entrega_domicilio` for delivery orders and `presencial` for pickup and counter orders. For delivery, SEFAZ requires the buyer identification and address; `web-nf` enforces this at intake (08, section "Pre-send validation").

## 3. NFSe — services, the fragmented world

Marmitop does not issue NFSe. This section exists because the goal requires it, and because a future "services" product (catering, events) would need it.

* NFSe is a municipal document taxed by ISS. Historically each municipality ran its own system, so formats and rules differ.
* **ABRASF "Modelo Nacional"** is the common reference. Many vendors implement it with local changes. Typical SOAP operations: `RecepcionarLoteRps` (async batch, then poll), `ConsultarSituacaoLoteRps`, `ConsultarLoteRps`, `ConsultarNfsePorRps`, `CancelarNfse`. The RPS (provisional service receipt) becomes the NFSe within a period set by the municipality. **VERIFIED-SECONDARY**.
* Municipalities differ in SOAP style (RPC/literal or document/literal), whether the XML signature is mandatory, error tables, and deadlines.
* **Nacional standard.** The national NFS-e (Receita Federal, ABRASF, CNM) uses a DPS (Declaração de Prestação de Serviço) sent to the national data environment (ADN), which returns the NFSe. Transport is REST plus a signed XML document. The official technical library lists, for production: Manual de Contribuintes — Emissor Público v1.2 (October 2025), ADN API guide, XSD package v1.01 (2026-02-09), and layout annexes (Annex I: DPS). **VERIFIED-PRIMARY** (gov.br documentation page). A "produção restrita" environment exists for tests. **VERIFIED-PRIMARY** (documentation link and portal notice).
* The gov.br NFS-e home page names the Comitê Gestor da NFS-e and RFB; the page does not say who runs the ADN. The `web-nf` research ties LC 214/2025 to mandatory adoption from 2026. **UNVERIFIED** here (not stated on the pages fetched).

### Municipality provider example: Publica, Irani/SC

* The portal (`nfse1.publica.inf.br/irani_nfse`) shows a notice: from 2026-07-01 all invoices must be issued on the National Portal; the municipal system keeps consulting, checking, and ISSQN calculation, and imports national notes automatically. **VERIFIED-PRIMARY** (read 2026-10-13).
* The downloads page lists: the user manual (86 pages), the RPS integration manual, the DIR integration manual, XML examples, XML Schema v3.01 (`schema_nfse_v03.xsd`), a schema validator, and the WSDL at `irani_nfse_integracao/Services?wsdl`. **VERIFIED-PRIMARY**.
* Technical facts from the `web-nf` research, read there from the integration manual v7.5 and the live WSDL: SOAP 1.1 RPC/literal, payload in CDATA, `SOAPAction` equal to the operation name, async `RecepcionarLoteRps` with polling, enveloped XMLDSig (RSA-SHA1), no mTLS, error table `E1`–`E284`, RPS to NFSe within 10 days. **VERIFIED-SECONDARY** here (not re-read by this project).
* The user manual PDF was fetched but WebFetch could not extract its text; its 86-page length was confirmed, its contents were not re-read.

## 4. Digital signature and certificates

* The issuer signs the XML with an **A1 e-CNPJ** certificate: a PKCS#12 file (`.pfx`/`.p12`) that holds the private key and the ICP-Brasil chain. It is protected by a password and is valid for about 12 months. An e-CPF identifies a person; an e-CNPJ identifies the company. A3 certificates live on a token or card and cannot be uploaded to a server, so they do not work for cloud issuers.
* NFe and NFC-e use an enveloped XMLDSig over the `infNFe` element, with plain C14N, RSA-SHA1, and a SHA-1 digest. **VERIFIED-SECONDARY**.
* SEFAZ web services require mutual TLS: the client certificate takes part in the HTTPS handshake. **VERIFIED-SECONDARY**.
* The `infNFeSupl` block (QR Code and query URL) sits outside the signed part. **VERIFIED-SECONDARY**.
* **Marmitop never holds the certificate.** The restaurant uploads its A1 file to `web-nf` (`POST /v1/certificates`). Marmitop only learns of a missing certificate through the `certificate_missing` error (08).
* An expired certificate is the most common cause of a sudden stop in issuing. The Settings screen should show the certificate expiry that `web-nf` reports, when it reports one. Whether `web-nf` exposes it today is not confirmed; see 08, open questions.

## 5. Homologação versus produção

* SEFAZ has two environments: `tpAmb = 2` homologação (tests, no legal value) and `tpAmb = 1` produção. Each has its own endpoints. **VERIFIED-SECONDARY**.
* The CSC is per environment. A homologação CSC does not work in produção.
* Homologação documents carry the text "NF-E EMITIDA EM AMBIENTE DE HOMOLOGAÇÃO - SEM VALOR FISCAL" in the first item. **UNVERIFIED** (memory; confirm in the MOC annex).
* `web-nf` mirrors this with API key prefixes: `nfk_test_` for homologação and `nfk_live_` for produção. Marmitop stores `integrations_fiscal.environment` and shows a visible "Homologação" badge, so that a test invoice is never mistaken for a real one.
* Municipal NFSe systems also run test environments (Publica has `nfse-teste.publica.inf.br`; the Nacional has "produção restrita"). These matter only if Marmitop later issues NFSe.

## 6. How Marmitop reaches SEFAZ

```
Marmitop  --JSON-->  web-nf  --signed XML, mTLS-->  SEFAZ (UF authorizer)
   ^                    |                                  |
   +---- webhook / poll +<------- protocolo / rejection ---+
```

Marmitop sends `POST /v1/invoices` and receives `202 queued`. `web-nf` builds the XML, signs it, sends it, and reports `authorized`, `rejected`, `denied`, or `failed` by webhook (`X-NF-Signature`) and by `GET /v1/invoices/{id}`. 08 covers the field mapping and the error table.

## 7. WhatsApp Business (Meta Cloud API)

* **Cloud API.** Meta hosts the WhatsApp Business API. A business connects a phone number (`phone_number_id`) and sends messages over HTTPS. Inbound messages and status updates arrive as webhooks from Meta, signed with `X-Hub-Signature-256`.
* **Customer service window (24 hours).** When a customer messages the business, a 24-hour timer starts. Each new customer message resets it. While the window is open, the business may send any free-form message type. After it closes, only approved templates are allowed. Both need the user's opt-in. **VERIFIED-PRIMARY** (Meta documentation, "Send messages", read 2026-10-13).
* **Templates.** A template is pre-approved by Meta and has a category: Authentication, Marketing, or Utility. The category sets the price. A template must have status `APPROVED` to be sent. "Template messages are the only type of message that can be sent to WhatsApp users outside of a customer service window." **VERIFIED-PRIMARY** (Meta documentation, "Template overview").
* **What this means for a restaurant.** An attendant can answer a customer who wrote in the last 24 hours with free text. To write first, or after 24 hours (for example, "your order is ready" a day later), the restaurant needs an approved template. The automatic messages in v1 (`welcome`, `closed`, `order_received`) are replies to an inbound message, so they fall inside the window.
* **How `backend-uatis` abstracts it** (read from `backend-uatis/docs/06.api-spec.md`):
  * `POST /v1/messages` takes exactly one of `text`, `media`, or `template`. It inserts an outbound row with status `pending` and returns `201`. A dispatcher inside `backend-uatis` calls Meta.
  * A free-form message outside the window returns `422 outside_service_window`. A disconnected line returns `422 whatsapp_disconnected`. An unknown template returns `template_not_found`.
  * Templates are managed through `/v1/templates` (create via the Meta-backed path, list approved ones).
  * Inbound messages reach `backend-uatis` through its own Meta webhook. It stores them and exposes `GET /v1/messages` and `GET /v1/conversations`. Customer webhooks (`message.created`, `message.updated`, `conversation.updated`) carry `X-Uatis-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "t.body")>`, with a 300-second tolerance.
  * Auth: `Authorization: Bearer obk_live_…` or `obk_test_…`.
* **Consequence for Marmitop (ADR-002).** Marmitop never calls Meta and never holds Meta credentials. The `WhatsAppGateway` port maps `outside_service_window` to a clear message in the chat UI: "A janela de 24 horas fechou. Só é possível enviar um modelo aprovado." In v1 the chat sends text only; a template picker is a follow-up.

## 8. Design consequences

1. NFC-e is the default document for meals; NFe is the exception for company buyers (ADR-003, ADR-013).
2. Marmitop is a client of `web-nf`. It needs no XML, no certificate, and no SEFAZ endpoint list. It needs a precise payload and a good error table (08).
3. Delivery orders need the buyer CPF/CNPJ and a structured address. The data model stores a structured address (`cep`, `logradouro`, `numero`, `bairro`, `uf`, `codigo_municipio`) for this reason (ADR-016).
4. Fiscal codes (NCM, CFOP, CSOSN, PIS/COFINS CST) are per restaurant data, not code constants. Defaults live in `integrations_fiscal`; menu items override NCM and CFOP.
5. Environment is a first-class setting. The UI shows homologação clearly.
6. The WhatsApp 24-hour rule is enforced upstream, and Marmitop checks it first (ADR-014). It reads the customer's last inbound message, sends free text inside the window, and sends an approved template for `order_received` outside it.
